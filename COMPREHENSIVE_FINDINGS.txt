EXECUTIVE SUMMARY

ROOT CAUSE IDENTIFIED: RPC Context Boundary Violation

The POPSLoader parent-context HDD ELF loading path (elf.c lines 627-898) fails
silently because it attempts to use RPC services (fileXio) set up in the parent
EE context from within a child EE context created by ExecPS2. This violates a
fundamental PS2 architectural constraint: RPC client connections are per-context
and become invalid across ExecPS2 boundaries.

SILENT FAILURE MECHANISM:
  1. fileXioInit() called in parent creates RPC client in parent context
  2. ExecPS2() switches to POPSTARTER's context
  3. POPSTARTER has no RPC client - parent's is invalid
  4. POPSTARTER cannot access files or output debug logs
  5. Black screen with zero debug output

SOLUTION AVAILABLE: Use POPSLoader's embedded loader path, which is already
implemented and working. This path initializes RPC services in the embedded
loader's context (after ExecPS2), ensuring they are valid for that context.

TECHNICAL ANALYSIS
================================================================================

CONSTRAINT 1: RPC Client Connections Are Per-Context
──────────────────────────────────────────────────────

PS2 Architecture:
  - EE (Emotion Engine) runs application code
  - IOP (I/O Processor) runs kernel and device drivers
  - RPC (Remote Procedure Call) connects EE to IOP services
  - SifInitRpc() establishes this connection in CURRENT EE CONTEXT
  - fileXioInit() creates RPC client for file I/O

Implications:
  - Each EE context has its own RPC state
  - ExecPS2() creates new EE context (new task/thread)
  - Parent's RPC state CANNOT be used by child
  - Each context must initialize its own RPC state if needed

Evidence: Both working implementations respect this constraint.


CONSTRAINT 2: fileXioInit() Must Be Called In Execution Context
────────────────────────────────────────────────────────────────

Why it matters:
  - fileXioInit() creates RPC CLIENT in current EE context
  - Client is stored in thread-local or context-local storage
  - Child context doesn't have access to parent's client

Broken approach:
  fileXioInit() in parent
  ExecPS2() to child
  Child tries to use parent's fileXio client
  Result: CRASH or HANG (no RPC client in child)

Correct approaches:
  A) Call fileXioInit() in child context (embedded loader approach)
  B) Don't use fileXio after ExecPS2 (wLaunchELF approach)

Evidence: Embedded loader at line 375 calls fileXioInit() FIRST.


CONSTRAINT 3: Module Loading Is IOP-Level (Global)
────────────────────────────────────────────────────

Important distinction:
  - SifExecModuleBuffer() loads module into IOP (global)
  - All EE contexts can ACCESS loaded modules
  - But RPC connections to those modules are PER-CONTEXT

Example:
  Parent loads ps2hdd, ps2fs modules via SifExecModuleBuffer
  Modules exist globally on IOP
  Parent mounts partition via fileXio (RPC in parent context)
  Child inherits IOP modules (can see them)
  Child DOES NOT inherit parent's RPC client (per-context)
  Child cannot use fileXio unless it creates its own RPC client

This explains why partition appears "mounted" but child can't access it.


CONSTRAINT 4: IOP Mount State vs. EE RPC Client
─────────────────────────────────────────────────

IOP Side (global):
  - Partition is mounted at pfs0: on the IOP
  - All IOP filesystem operations work

EE Side (per-context):
  - fileXio RPC client is per-context
  - EE cannot access IOP filesystem without valid RPC client
  - Parent's RPC client is not inherited by child

Consequence:
  - Partition IS mounted globally
  - Parent's RPC client IS valid
  - But child's context has NO RPC client
  - Child sees mounted partition on IOP but cannot access it (no RPC)

WHY SILENT FAILURE OCCURS
================================================================================

Chain of events:

1. Parent Context Execution (POPSLoader parent path)
   ✓ Modules loaded successfully
   ✓ RPC initialized
   ✓ fileXioInit() called (creates RPC client in parent)
   ✓ Partition mounted via fileXio
   ✓ SifLoadElf() loads ELF successfully
   → ExecPS2() called

2. Context Switch to POPSTARTER
   ✗ New EE context created
   ✗ Parent's RPC client state is LOST
   ✗ Parent's fileXio RPC connection is INVALID

3. POPSTARTER Initialization
   ✗ Tries to access files
   ✗ Attempts fileXio operation
   ✗ fileXio fails (no RPC client in this context)
   ✗ File access returns error or hangs
   ✗ POPSTARTER cannot initialize

4. Debug Output Failure
   ✗ Debug logs also use fileXio
   ✗ fileXio not working, no RPC client
   ✗ Debug output fails
   ✗ No output on console

5. Silent Black Screen
   → POPSTARTER crashes or hangs silently
   → No debug output (fileXio failed)
   → Black screen, no error message
   → User sees only silent failure

This explains:
  - Why it's silent (debug also uses fileXio)
  - Why it's black screen (POPSTARTER can't initialize)
  - Why it's reproducible (always fails when using parent-context path)
  - Why embedded loader works (fixes the RPC context issue)

================================================================================
CONCLUSION
================================================================================

The POPSLoader HDD ELF loading silent failure is caused by a fundamental
architectural violation: RPC client connections created in the parent EE
context are invalid in the child EE context created by ExecPS2.

This is NOT a bug in module loading, partition discovery, or ELF parsing.
The parent successfully loads modules, mounts the partition, and loads the
ELF. The failure occurs when POPSTARTER tries to initialize in its own
context without a valid RPC client.

The solution is simple: use the embedded loader path, which is already
implemented and working correctly in the same codebase. This path initializes
RPC services in the embedded loader's context (after ExecPS2), ensuring they
are valid for that context.
