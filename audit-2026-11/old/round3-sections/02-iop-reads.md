- **Problem:** Repo-wide grep (READ) finds no caller of `unfs4_init_context` anywhere — not in `nfsman.c`, not in the host tests, not elsewhere. `nfsman` builds its context itself (`nfsman.c:420-473`: `calloc`, `nfsman_tcp_connect` at `nfsman.c:375-418`, then `unfs4_mount`). - **Benefit:** ~33 lines of misleading connect code gone; one connect path, the one with the port and timeout rules.

### R3B-03 / smbman's `FileTimeToDate` computes wrong calendar dates — and it is the third, divergent copy of a conversion the other two drivers do correctly / Category 6 (Bug) / 2 (Duplication)
- **Location(s):** `iop/smbman/smb_fio.c:563-615` (`FileTimeToDate`), called only by `smb_statFiller` at `smb_fio.c:617-627`. Correct counterparts: `iop/smb2man/smb2man.c:1015-1046` (`smb2man_pack_time`) and `iop/nfsman/nfsman.c:849-879` (`nfsman_pack_time`) — both use Howard Hinnant's `civil_from_days`; smb2man's even takes the same FILETIME input.
- **Problem:** The hand-rolled algorithm (divide by 365, subtract a leap-day estimate, then walk months with a strict `days > daysPerMonth[i]` test at `smb_fio.c:588`) is wrong on ordinary dates. Verified by executing a C-width-faithful Python replication of `smb_fio.c:563-615` this session: **80 of 240 sampled timestamps (1995–2034, six days per year) convert incorrectly** — e.g. 1995-03-01 → "1995-02-29" (a date that does not exist), 2000-03-01 → "2000-02-30", 1995-12-31 → day 146 of January 1997 (day and year both wrong). (READ for the code; the replication is host-arithmetic evidence, not a console test.) Every `smb1:` stat/dirent timestamp passes through this function. Secondary discrepancy in the same filler (READ): `smb_fio.c:621` maps `info->Change` to `stat->mtime` and never reads `info->LastWrite` (`iop/smbman/smb.h:298`), while `smb2man_fill_stat` (`smb2man.c:1059-1071`) uses the write time for `mtime` — the same file shows different modification times via `smb:` and `smb1:` (INFERRED impact: only the displayed/sorted mtime differs).
- **Fix:** Delete `FileTimeToDate`'s algorithm and use the in-tree Hinnant conversion the other two drivers already carry (`smb2man_pack_time` is a drop-in: same FILETIME input, same 8-byte output layout); take `mtime` from `LastWrite` while there. This is deletion-and-adoption, not a fourth implementation.
- **Benefit:** Correct dates from the SMB1 driver; one conversion algorithm left in the tree to maintain.
- **Effort:** S. **Risk:** Low (the replacement is already exercised by two drivers). **Confidence:** High for the wrongness (executed replication); High (READ) for the duplication.

### R3B-04 / smbman's read/write/dread/lseek dereference the handle without the validation its own close performs — and neither read nor write rejects a negative size / Category 6 (Bug)
- **Location(s):** The validation that exists: `iop/smbman/smb_fio.c:386-387` (`smb_close`: `fh == NULL || fh->f != f` → `-EBADF`). The unguarded dereferences: `smb_read` `smb_fio.c:429-436`, `smb_write` `smb_fio.c:453-459`, `smb_dread` `smb_fio.c:696,711`, `smb_lseek64` `smb_fio.c:872-878`. Missing size checks: `smb_fio.c:435-440` and `smb_fio.c:464`, vs both sibling drivers' explicit `if (size < 0) return -EINVAL;` (`smb2man.c:874,915`; `nfsman.c:701,741`) and their generation-checked slot lookup on every op (`smb2man.c:751-763,828-839`; `nfsman.c:570-579,661-677`).
- **Problem:** `smb_read` dereferences `fh` in its first test (`fh->smb_fid`, :432) and computes the clamped size from `fh->position`/`fh->filesize` *before* taking the IO lock (:435-438), while `smb_close` frees and `memset`s that same handle under the lock (:389-401) — a stale or NULL `privdata` that `smb_close` would have rejected is a wild dereference here. If `position > filesize` ever holds, :436 computes a negative `size` and passes it to `smb_ReadFile`, whose loop simply returns the negative count as its result (`iop/smbman/smb.c:1155-1172`) — a nonsense pseudo-error instead of `-EINVAL`. Triggerability depends on ioman/EE caller behaviour (INFERRED); the asymmetry itself is READ and total: of the three network drivers in this tree, only the SMB1 one trusts `privdata` blindly.
- **Fix:** Give `smb_read`/`smb_write`/`smb_dread`/`smb_lseek64` the same two-line guard `smb_close` already has, move the size clamp inside the lock, and add the siblings' `size < 0` rejection. No new helper needed — the pattern is already in the file.
- **Benefit:** A stale handle on `smb1:` returns `-EBADF` like everywhere else instead of dereferencing freed state on the IOP.
- **Effort:** S. **Risk:** Low. **Confidence:** High (READ) for the missing checks; Medium for practical triggerability (INFERRED).

### R3B-05 / smbman's `lseek64` ignores the SEEK_END offset, accepts negative positions, and the 32-bit `lseek` truncates positions past 2 GiB / Category 6 (Bug)
- **Location(s):** `iop/smbman/smb_fio.c:869-905` (`smb_lseek64`), `smb_fio.c:421-424` (`smb_lseek`). Correct counterparts: `smb2man.c:955-1010` and `nfsman.c:790-844` — both compute `base + offset`, reject a negative result, and make the 32-bit wrapper return `-EOVERFLOW` above 2 GiB (`smb2man.c:1004-1009`, `nfsman.c:838-843`).
- **Problem:** Three divergences, all READ: (1) `SEEK_END` at `smb_fio.c:891-893` sets `r = fh->filesize` and discards `pos` entirely, so `lseek(fd, -4096, SEEK_END)` — the standard tail-read idiom — lands at end-of-file on `smb1:` and at filesize−4096 on the other two drivers. (2) `SEEK_SET` (:884-890) and `SEEK_CUR` (:877-883) test only the upper bound, so a negative result is stored into `fh->position` (:899) and the next read/write hands a negative `s64` offset to the SMB wire fields (INFERRED wire effect from `iop/smbman/smb.c:1193-1194`'s u32 split). (3) `smb_lseek` (:421-424) casts the `s64` result to `int` with no overflow guard; positions up to `filesize` are legal in this driver, and `filesize` is a server-supplied `s64`, so a >2 GiB file seek truncates to a negative "error-looking" value.
- **Fix:** Adopt the siblings' seek body: `base + offset`, reject `< 0`, and the `-EOVERFLOW` guard in the 32-bit wrapper. Deletion of divergence, no new logic.
- **Benefit:** `smb1:` seeks behave identically to `smb:`/`nfs:`; tail reads work; large-file seeks stop lying.
- **Effort:** S. **Risk:** Low. **Confidence:** High (READ).

### R3B-06 / smbman's `dread` copies a server-supplied directory name with a `strncpy` that can leave `dirent->name` unterminated / Category 6 (Bug)
- **Location(s):** `iop/smbman/smb_fio.c:751` (`strncpy(dirent->name, info->FileName, SMB_NAME_MAX)`; `SMB_NAME_MAX 256` at `smb_fio.c:77`). The source is a flexible-array member fed from the server reply (`iop/smbman/smb.h:312-320`: the search buffer explicitly accommodates names up to ~3.8 KB). Safe counterparts in the same audit set: `nfsman.c:1020-1021` (copy at size−1 plus a forced NUL) and `smb2man.c:1289` via `smb2man_name_utf8` (always NUL-terminates within `outmax`).
- **Problem:** `dirent` is zeroed at `smb_fio.c:704`, so termination survives only while the name is shorter than 256 bytes. A server returning a name of ≥256 bytes — permitted by this driver's own search-buffer sizing — makes `strncpy` fill every byte of `dirent->name` with no NUL, and EE consumers treat that field as a C string (e.g. the `strcmp` filters in `src/filer.c`). A compromised or merely long-name-serving SMB1 server is within the threat model these drivers were hardened against in round 2.
- **Fix:** Copy the nfsman way, two lines at the same site: bound at `sizeof(dirent->name) - 1` and write the final NUL explicitly.
- **Benefit:** Every `smb1:` directory entry is a valid C string by construction, like the other two drivers'.
- **Effort:** S. **Risk:** Low. **Confidence:** High (READ) for the pattern; trigger requires a ≥256-byte server filename (INFERRED reachability — unusual for SMB1 long names, but the buffer design admits it).

### R3B-07 / `smb_closeAll` sends server CLOSE for directory search handles and frees no handle slots at logoff / Category 6 (Bug)
- **Location(s):** `iop/smbman/smb_fio.c:407-418` (`smb_closeAll`); callers `smb_fio.c:977` (`smb_LogOff`) and `smb_fio.c:1087` (`smb_CloseShare`). Contrast `smb_close` at `smb_fio.c:391-399`, whose comment and guard exist precisely to handle this correctly.
- **Problem:** Two defects, both READ. (1) `smb_closeAll` calls `smb_Close` for every slot with `smb_fid != -1`, with no `O_DIROPEN` exclusion — but a directory handle's `smb_fid` is a *search ID*, assigned from `info->SID` at `smb_fio.c:725`, not a file FID; `smb_close` guards against exactly this (`fh->mode != O_DIROPEN`, :394). (2) Unlike `smb_close` (:397-399), `smb_closeAll` clears nothing — no `memset`, `fh->f` and `f->privdata` survive — so after a logoff/close-share the 32 slots stay "open" holding FIDs of a torn-down tree. After a later logon, `smb_read`'s only validity test is `fh->smb_fid == -1` (:432), so a stale handle addresses whichever file the *new* session happens to give the same FID (INFERRED impact; the slot leak and the SID-close are READ).
- **Fix:** Make `smb_closeAll` reuse `smb_close`'s predicate and slot-clearing (both already in this file): skip `O_DIROPEN` handles' server close, and `memset` each slot / clear `privdata` exactly as :397-399 does.
- **Benefit:** Logoff stops issuing bogus CLOSEs and stops leaking the handle table across sessions; one definition of "end a handle" in the file.
- **Effort:** S. **Risk:** Low. **Confidence:** High (READ) for the mechanism; Medium (INFERRED) for the cross-session FID-aliasing harm.

### R3B-08 / `DMA_sendEE` spins forever with no timeout, called with the SMB IO lock held / Category 5 (Performance / blocking)
- **Location(s):** `iop/smbman/smb_fio.c:908-926`; sole call site `smb_fio.c:1037` inside `smb_GetShareList`, reached from `smb_devctl` (`smb_fio.c:1140-1142`), which holds `smb_io_lock` for the whole dispatch (`smb_fio.c:1123-1164`).
- **Problem:** Two unbounded loops: `while (!id)` retrying `sceSifSetDma` (:919-923) and the pure spin `while (sceSifDmaStat(id) >= 0);` (:924-925) — no timeout, no yield, no error path; the function returns `void`, so the caller cannot learn of failure. If the DMA never completes (a bad `EE_addr` in the devctl argument is INFERRED as one route; an EE-side stall is another), the `smb1:` device wedges with the IO semaphore held, which also starves the keepalive thread waiting on the same semaphore (`smb_fio.c:182-219`). Both newer drivers bound every wait (`smb2man.c:90-145`, `nfsman.c:79-124`); this is the one unbounded wait left among the four files.
- **Fix:** Bound both loops with a retry budget and return an error, propagating it through `smb_GetShareList` (its only caller chain already returns `int`). Behaviour on success is unchanged.
- **Benefit:** A failed share-list DMA becomes an error return instead of a permanently hung network device.
- **Effort:** M (signature change from `void` to `int`, one call site). **Risk:** Low. **Confidence:** High (READ) for the unbounded loops; INFERRED for the hang scenario.

### R3B-09 / smbman's `devctl` dereferences caller buffers with no NULL or length validation — the check both sibling drivers perform first / Category 6 (Bug, robustness)
- **Location(s):** `iop/smbman/smb_fio.c:1114-1167`: `arglen`/`buflen` are explicitly cast away (:1120-1121), then `arg` is dereferenced for GETPASSWORDHASHES (:1128), LOGON (:1133), GETSHARELIST (:1141), OPENSHARE (:1145) and ECHO (:1153, whose handler passes the caller-supplied `echo->len` straight to `smb_Echo` at :1099-1102), and `bufp` is written through for GETPASSWORDHASHES (:1128) and QUERYDISKINFO (:1157). Sibling pattern: `smb2man.c:1550-1552` and `nfsman.c:1311-1313` reject `arg == NULL || arglen < sizeof(...)` before any cast, and their connect handlers additionally `memchr`-validate every string field (`smb2man.c:1498-1500`, `nfsman.c:1265-1266`).
- **Problem:** A short or NULL devctl buffer from any EE caller becomes an out-of-bounds read (or, for the hash/disk-info outputs, write) on the IOP. Honest mitigation (READ): the in-tree EE caller is clean — `src/smb_shares.c:278-324` zero-fills each struct and passes exact `sizeof` for every command it uses, and passes `NULL` only for LOGOFF, which is never dereferenced. So there is no in-tree trigger; this is an interface-robustness gap on a long-lived devctl API that other EE homebrew also calls, and it is the only one of the three drivers still missing the check. (Struct field sizes live in the SDK's `ps2smb.h`, not in this repo, so per-field termination claims are not made.)
- **Fix:** Copy the siblings' guard: per-command `arg`/`bufp` NULL and `arglen`/`buflen` minimum checks at the top of the switch — a few lines, pattern already in the tree twice.
- **Benefit:** The SMB1 devctl interface fails with `-EINVAL` instead of dereferencing whatever the caller passed, matching `smb:` and `nfs:`.
- **Effort:** S. **Risk:** Low. **Confidence:** Medium (READ for the missing checks and the sibling contrast; INFERRED for exploitability, with the in-tree caller verified clean).

### R3B-10 / smbman's `chdir` reads one byte before its path buffer for root/empty directory names / Category 6 (Bug, minor)
- **Location(s):** `iop/smbman/smb_fio.c:838,846` (`path[strlen(path) - 2]` and `path[strlen(path) - 1]`), fed by `prepare_path` at `smb_fio.c:834`; buffer layout at `smb_fio.c:91-99` (`smb_curdir` immediately precedes `smb_curpath`).
- **Problem:** `prepare_path`'s visible C-string can be a single backslash: with `smb_curdir` empty and a dirname of `""` or `/`, the prepared string's `strlen` is 1 (the curdir backslash; the copied byte is the terminator — see the -051 revisions note), so `path[strlen(path) - 2]` is `path[-1]`, a read one byte before `smb_curpath`. Today that byte is the last byte of the adjacent `smb_curdir` static (READ, from the declaration order), which is 0 in practice, so no wrong branch is taken — this is an out-of-bounds read kept benign by static layout, not a demonstrated fault.
- **Fix:** Guard the two tests by length (`strlen(path) >= 2` for the `..` test, `>= 1` for the `.` test) — the root case then falls into the normal query branch, which handles it.
- **Benefit:** Removes the last unguarded index in the file's path handling; behaviour for real `.`/`..` names unchanged.
- **Effort:** S. **Risk:** Low. **Confidence:** Medium (READ for the index arithmetic and the strlen-1 construction; INFERRED-benign for today's impact).

## Revisions note — new evidence on LAUNCHSTATION-051 (`prepare_path`, `iop/smbman/smb_fio.c:305-334`) — NOT a new finding

Full end-to-end reading of the function adds evidence in both directions:

- **Narrowing (against the worst reading of -051):** once the `strcat` at :312 survives, the output *is* terminated by construction, twice over. The copy loop's condition is `p <= p2` (:325) where `p2` points **at** the source string's terminating NUL (:320), so the NUL is copied into `full_path` as data; :330-331 then write a backslash and a second NUL after it, and the loop guard (`max_path - i - 2 > 0`) keeps those two writes in bounds. The -051 hazard is therefore confined to exactly the :311-312 idiom: if `smb_curdir` ever reaches length ≥ `max_path - 3` unterminated, `strncpy` leaves no NUL and the `strcat` walks off — the input side, not the output side.
- **Strengthening (new defect inside the same function):** the trailing-slash strip at :320-322 is dead code that can never execute — `p2` is initialised to `&path[strlen(path)]`, i.e. at the NUL terminator, and NUL is neither `'\\'` nor `'/'`, so the `while` body never runs. Consequently `prepare_path` never strips trailing slashes and never actually appends the trailing backslash its comments (:319, :329) describe — the :330 backslash lands after the embedded NUL, invisible to every C-string consumer. Callers compensate inconsistently (e.g. `smb_dopen` re-derives the last visible character itself at `smb_fio.c:659,673`). This is comment/code divergence plus a dead loop in the very function -051 flagged, and it means any future fix to -051 should rewrite the tail handling, not just add the one terminating line.

- **smb2man `sprintf(unc, …)` (`smb2man.c:577`)** — `unc` is sized `2 + sizeof(ipstr) + 1 + sizeof(share)` and `smb2man_parse_url` additionally caps the combined tree-connect string at 127 bytes. Fits by construction.
- **nfsman open filehandle copy (`nfsman.c:639`)** — length comes from a handle that only `get_fh`-validated paths can produce (round-2 checked-clean), and the destination is exactly `4 + UNFS4_MAX_FH`. Fits.
- **unfs4 ignored socket return values (`unfs4.c:257-267`, `unfs4.c:489-535`)** — a failed read/write closes the socket via `socket_failed`, and `unfs4_rpc` checks `fd < 0` before trusting any reply byte (:538-541); the stale-buffer case is caught by the record-mark test. Failure is handled, just indirectly.
- **unfs4_rpc reply-drain loop (`unfs4.c:533-535`)** — reuses the same buffer offset without advancing it, which looks like an overflow; each `read_reply` is clamped to the remaining capacity from that offset and total reply size was pre-bounded against `buf + indata`. It is an overwrite-drain, in bounds.
- **unfs4_readdir `dir->de.name[len] = 0` (`unfs4.c:757`)** — writes over name padding or attribute bytes that `get_attrs` has already copied out, and `dir->pos` skips past both. Intentional, and commented as such.
- **smb_dopen's use of `sizeof(fh->name)` before `fh` is assigned (`smb_fio.c:659`)** — `sizeof` is unevaluated in C; no uninitialised pointer is dereferenced. The subsequent length arithmetic was verified to bound the `strcpy`/`strcat` sequence into the 256-byte field exactly (worst case fills it including the NUL).
- **smb2man root `dopen` partial allocation (`smb2man.c:1125-1145`)** — the `offsetof(..., data)` allocation spans every scalar field of the struct; the root path touches only `share`/`off`. Intentional and commented.
- **The two port parsers** (smb2man's hand loop `smb2man.c:1468-1472` vs `nfsman_number` `nfsman.c:1183-1203`) — both are overflow-safe (loop-condition cap + post-check; pre-multiply check respectively). Their contracts differ (nfsman's also parses uid/gid), so the resemblance is not filed as duplication.
- **Rename same-share prefix tests (`smb2man.c:1418-1423`, `nfsman.c:1153-1158`)** — `newrest[rv]` is only evaluated when `strncmp` matched the full name, so the index is in bounds (the NUL at worst). Safe.
- **unfs4 `.`/`..` handling (`unfs4.c:712-768`)** — the code does not filter dot entries despite the header comment in `unfs4.h`; the EE filer filters them itself (`src/filer.c:1106` and siblings), so there is no user-visible defect to file. Doc nit only.
- **smb_fio static storage** (three 1024-byte path buffers, the 4096-byte `SearchBuf`, the 32-slot `FHANDLE` table at `smb_fio.c:78-99`) — `smb_secpath` is genuinely needed simultaneously with `smb_curpath` by rename (:806-807), `SearchBuf` is only touched under the IO lock, and the handle count is a product limit; shrinking any of them is a behaviour change with no in-repo evidence of need. (Also noted for -044's context: smbman is the target *without* `--gc-sections`.)
- **`prepare_path` called before `smb_io_lock` at all eight call sites (`smb_fio.c:351,489,516,541,642,774,806-807,834`)** while `smb_curdir` is mutated under the lock in `smb_chdir` — a possible race on paper, but whether iomanX can dispatch this device's ops concurrently is not established by anything in this repo, so no race is claimed.
- **One global lock held across multi-chunk I/O and reconnects (smb2man/nfsman)** — request/response pairing on a single protocol context requires serialisation; per-share locks would *add* mechanism against the LESS-NOT-MORE rule, with no measured contention. Not flagged.
- **`smb_GetShareList`'s `UID == -1` check placed after its TreeConnect call (`smb_fio.c:1010-1018`)** — ordering nit; the in-tree EE never issues GETSHARELIST (grep, `src/`), and no failing path through it was demonstrated.
- **32-bit `lseek` wrappers in smb2man/nfsman (`smb2man.c:999-1010`, `nfsman.c:833-844`)** — negative errors from `lseek64` pass the `> 0x7fffffff` test untouched and return unchanged. Correct.
- **unfs4 TINY_TCP blocks (`unfs4.c:120-190`)** — preprocessor-excluded in this build (nfsman defines no `UNFS4_FEATURE_TINY_TCP`); vendored feature code for another target, not shipped dead code.
- **`smb_open`'s `strncpy(fh->name, path, SMB_NAME_MAX)` (`smb_fio.c:369`)** — a regular file handle's `name` is never read back as a string (only directory handles' names are used, and `smb_dopen` length-checks before its own copy), so the possible missing terminator has no consumer.
