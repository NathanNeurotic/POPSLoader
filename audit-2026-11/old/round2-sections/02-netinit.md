## 2. Duplicated sequences vs genuinely different stacks

**The load *order itself* is stack-determined, not repo-determined (READ) — this is the cleanest function-level result:**

| Stack family | Order | Who |
|---|---|---|
| NETMAN / SDK lwIP | DEV9 → NETMAN → SMAP → PS2IP (address applied *after*, via `ps2ip_setconfig`, or as PS2IP's own arg) | RiptOPL menu (`netsupport.cpp:192-219`); Launchstation modern (`init.c:656-677`) |
| SMSTCPIP / v1.0 (no NETMAN) | DEV9 → **PS2IP first → SMAP second, SMAP takes the address (+link mode)** | Launchstation legacy (`init.c:639-653`); SMS (`SMS_IOP.c:576-580`); RiptOPL **in-game** (`ee_core/src/iopmgr.c:264-265`) |
| UDPFS ministack (no IP stack at all) | DEV9-init → `udpfs_smap` → `udpfs_ministack("ip=…")` → `udpfs_ioman` | All three repos, three separate implementations (above) |

So: **RiptOPL contains both families** — its menu stack is Launchstation-modern's sibling, its in-game stack is SMS's sibling. The task's framing ("RiptOPL SMSTCPIP vs Launchstation modern") is only half the picture: SMSTCPIP in RiptOPL is the *game* stack (`ingame_smstcpip_irx`), while its menu runs the same NETMAN+lwIP family as Launchstation modern. Launchstation's dual stack (Round-1 `LAUNCHSTATION-003`) is a *runtime* duality inside one function (`load_ps2ip` branches on `ps2dev9_variant`); SMS's duality (Round-1 `SMS-018`) is *vendored-source* duality — SMSTCPIP (lwIP, `iop/SMSTCPIP/`) for SMB/host plus the UDPFS ministack (`iop/SMSUdpfs/`) — selected by `s_NetOwner`, never co-resident.

**Genuinely duplicated (same hardware steps, rewritten):** (a) DEV9-first + SMAP + bring-IP-up, written **5 times** across the three repos (RiptOPL menu, RiptOPL in-game, LS modern, LS legacy, SMS) plus **3 more** for the UDPFS shape; (b) `IPCONFIG.DAT` parsing of the identical 3-field format, written 3 times (LS `main_startup.c:55-143`, SMS `SMS_IOP.c:1368-1427`, RiptOPL `core/config.cpp:752-754`) with LS and SMS even sharing the compiled-in defaults byte-for-byte; (c) the IOP-reset-as-stack-switch, which SMS's `SMS_IOPNetSwitch` header openly says mirrors Launchstation's `switchNetworkStack` (`SMS_IOP.c:1760-1775`).

**Genuinely different (not duplication):** everything after the loads. RiptOPL's apply-config/link-wait/DHCP/DNS/teardown layer (`netsupport.cpp:110-147,255-305,404-495`, ~200 lines) has **no counterpart at all** in the other two repos — they have nothing to deduplicate it against. Conversely LS's variant-switch-resets-DEV9 and SMS's boot-time DEV9 power decision are policy, not stack code.

## 4. Steps one repo does that the others omit

- **RiptOPL only:** DHCP end-to-end (config flag, `dhcp_enabled` setconfig, BOUND wait, status API); DNS server application; link-mode setting *and* the pre-load mode attempt to avoid double-init (`netsupport.cpp:208-209`); the second link wait after a mode change (`:133-136`); non-reset teardown (`NetManDeinit + ps2ip_deinit`); NIC interlocks against its own UDPBD/UDPFS chains at runtime (`:178-190`); DEV9 refcounting with latch-only-on-success so a failed load can be retried (`system.cpp:243-262`).
- **Launchstation only:** a whole second DEV9/PS2IP/SMAP family behind one flag, including forcing an IOP reset when the *DEV9 variant* changes (`init.c:503-511`); `dev9_poweroff_irx` arming — but storage-only, so a network-only session runs without it (callers `:741,795,2554` vs none in `load_ps2ip`); dashboard DNS *synthesis* (gateway → `1.1.1.1`/`8.8.8.8`) (`init.c:2850-2875`); `ps2ips`/`ps2ip_init()` quarantined to the dashboard path, so its SMB stack runs with no EE socket bind at all (`init.c:2908` is the sole `ps2ip_init()`).
- **SMS only:** DEV9 loaded at boot before config is even known, then **powered down at boot** if no auto-start flag needs it (`SMS_IOP.c:1457,1663-1672`); net start as an *ioctl on a resident driver* (`DEV9CTLINIT`) rather than a module load — including the documented ordering trap that DEV9-init wipes SMAP's DMA callbacks, so it must precede `udpfs_smap` (`SMS_IOP.c:912-920,937-947`); link mode smuggled as a 4th SMAP argument; a dead declaration — `SMS_StartNetwork` is declared at `include/SMS.h:308` and defined **nowhere** in the tree (grep, READ); the real entry is `SMS_IOPStartNet`.
- **All three omit:** DHCP release on teardown (no `dhcp_release`/`dhcp_stop` anywhere — moot for LS/SMS, a real gap in RiptOPL, whose deinit goes straight to `NetManDeinit`); any link *debounce* (RiptOPL waits for first UP and re-waits once after a mode change; nobody waits for stability across two samples); any DEV9 power-*cycle* as a recovery step (failures escalate to IOP reset in LS/SMS, to error codes in RiptOPL — never to an off/on cycle of the adapter itself).

## 5. LESS-NOT-MORE verdict

**Keep separate. Do not build a shared network-init library — the divergence evidence says there is no longer a shared sequence to extract.**

Proof, in order of strength:

1. **The sequence is not common even at the load step.** Load order flips with stack family (SMAP→PS2IP for NETMAN/lwIP; PS2IP→SMAP for SMSTCPIP/v1.0, §2), and the address travels by a different mechanism in each (post-load `ps2ip_setconfig`, PS2IP module arg, SMAP module arg). A shared lib would need a per-family branch at nearly every step — i.e. it would contain all five existing sequences plus glue. That is *more*, not less.
2. **The policy layers don't overlap.** RiptOPL's init is mostly *post-load* policy (link wait 30 s, mode retries 3, DHCP wait, DNS, teardown) that LS and SMS simply do not have; LS's and SMS's init is mostly *ownership* policy (variant resets, `s_NetOwner`, boot power-down) that RiptOPL expresses differently (refcount + interlocks). Consolidating means exporting one repo's policy into two repos that never asked for it — speculative features, the exact failure mode of Round-1 findings `LAUNCHSTATION-003` / `SMS-018`, whose correct fix is *deleting* a stack, not abstracting over two.
3. **DEV9 ownership is architecturally incompatible:** refcounted shared resource (RiptOPL) vs variant-owned with reset-on-change (LS) vs pre-resident blob powered by ioctl and shut down at boot (SMS). This is the first step of every sequence and it cannot be unified without redesigning at least two repos' storage stacks, which also ride DEV9.
4. **The constants have already speciated** (§3): 100 vs 20/100 vs 1 on the identical `DDIOC_OFF`; 30 s vs absent vs absent on link wait. Unifying any of them is a *behaviour change on hardware*, per repo, disguised as deduplication — and per this audit's standing rule, none of it is verifiable without real PS2 hardware in the loop.

**What *is* worth consolidating (small, honest list):**
- **Nothing in code across repos.** Two cheap *intra*-repo fixes instead: (i) Launchstation should pick one `DDIOC_OFF` budget — its own poweroff path already documents 100 as the considered policy (`init.c:2598-2604` even cites RiptOPL), so the pre-reset 20 (`init.c:577`) is the outlier to align *inside* Launchstation; (ii) SMS's dead `SMS_StartNetwork` declaration (`include/SMS.h:308`) can simply be deleted.
- **The `IPCONFIG.DAT` format is already the shared artifact** — identical 3-field layout and (LS/SMS) identical defaults, parsed independently. Keep the *format* as the contract; the three parsers are ~40 lines each and two of them are entangled with repo-specific fallback policy (LS's mc-slot/MX4SIO refusal, SMS's CWD-then-card double read), so even this is not a clean extraction.
- If a future stack deletion happens (the Round-1 recommendation for both `LAUNCHSTATION-003` and SMS's vendored duality), the sequence count drops from 8 to 6 with zero new code — a strictly better LESS-NOT-MORE move than any shared library.

*Unverified / INFERRED notes:* Launchstation's PS2IP IRXs are precompiled blobs; any DHCP/link behaviour inside them was not read and is not claimed. IOP-internal timing of RiptOPL's and Launchstation's UDPFS ministacks was out of scope (EE probe behaviour only, which is READ). No hardware was run; all wait/retry figures are as written in source, not measured.
