## Reasoning for non-VERIFIED verdicts

### RIPTOPL-159 — WEAKENED
The loop-structure defect is exactly as filed: in `PadManager::start()` (src/core/pad.cpp:1155-1191) the `&padData_[padCount_]` reference is taken at :1175 inside the slot loop, the element's fields are written through it immediately, and the only `padCount_ >= MAX_PADS` break sits at :1188-1189 after a port's whole slot loop. So a slot iteration that begins with `padCount_ == 4` writes past `padData_[MAX_PADS]` (include/padmanager.h:84).
What does not survive is the filed reachability claim "The overflow is not gated on pads actually being present: `initialize()` returns 1 on every path … so `startOne()` succeeds for every opened slot and every slot increments the count." `startOne()` (pad.cpp:1136-1153) first calls `padPortOpen(pad->port, pad->slot, pad->padBuf)` and returns 0 if it returns 0 (:1140) — `initialize()` is only reached after a successful open, and `padCount_` increments only on `startOne()` success. Narrower truth: overflow requires four pads to have successfully opened (incrementing the count to 4) before an additional slot iteration in the same port — e.g. one opened pad on port 0 plus a multitap port whose first three slots open and whose fourth slot is then iterated. That is a real rig shape (the filed 1 + multitap example works under that condition), but it is gated on opened pads, not unconditional.

### RIPTOPL-164 — WEAKENED
Two of the three legs hold exactly: `ExceptionGetModuleName` returns 0 for an unlisted EPC and excepHandler.c:80 calls `strlen(module_name)` on it unconditionally; and the :86 `memcpy(buffer, frame, BUFFER_SIZE)` over-reads `frame` by 136 bytes (BUFFER_SIZE = `sizeof(exception_frame_t) + 4 + 4 + 128`, :12).
The buffer-overrun arithmetic as filed does not hold. The filed total ("`sizeof(exception_frame_t) + 149 + len` bytes written into a `sizeof + 136`-byte static, an overrun of at least 13 bytes plus the module-name length") sums the writes as if each advanced the cursor by its full length. In the code, after the memcpy the cursor advances only by `sizeof(exception_frame_t) / 4` words (:87), so the r_epc/len words (:89-91) and the name copy (:94) land inside the region the memcpy already wrote, not after it. Actual arithmetic: the memcpy starts at offset 4 and writes BUFFER_SIZE bytes, so it overruns the buffer by exactly 4 bytes regardless of name length; the name copy ends at offset `sizeof(frame) + 13 + len`, which overruns only if `len > 123`. Narrower truth: a guaranteed 4-byte static overwrite plus a 136-byte over-read from the memcpy, a name-length-dependent overwrite only for module names over 123 bytes, and the unconditional `strlen(NULL)` crash — the defect is real, the filed minimum overrun (13 + len) is not.
