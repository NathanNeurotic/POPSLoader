## (b) LAUNCHSTATION-085 — settlement

**-085 asked:** VMCMAN's `MCMAN_MAXSLOT=10` (`iop/vmcman/src/mcman-internal.h:105-109`, `#ifdef BUILDING_VMCMAN`, else 4) costs ≈33.8 KB of IOP statics over 4 — can any flow populate slots 4–9? **Answer: no in-tree flow can populate slots 2–9 at all; only slots 0 and 1 are ever populated. -085 is SETTLED: apply its proposed fix (drop the VMCMAN override to 4).** Evidence chain:

### B1. The device layer can only ever produce slots {0, 1, 8, 9} (READ)

`mcman_unit2card`, `iop/vmcman/src/mcdev.c:216-231`, VMCMAN branch `:221-223`:

```c
mcman_mc_port = 0;
mcman_mc_slot = unit & (MCMAN_MAXSLOT - 1);   // = unit & 9 = unit & 0b1001
```

For **any** `u32 unit`, `unit & 9 ∈ {0,1,8,9}`. Slots **2–7 are arithmetically unreachable through the device layer**, no matter what unit is presented. Complete unit table (VMCMAN, MAXSLOT=10): unit 0→0, 1→1, 2→0, 3→1, 4→0, 5→1, 6→0, 7→1, 8→8, 9→9, 10→8, 11→9, 12→8, 13→9, 14→8, 15→9, 16→0, … (period 16 in the low bits; the image is always {0,1,8,9}).

### B2. Every device operation funnels through that one mapping (READ)

`mcman_unit2card` has exactly **11 call sites, all in `mcdev.c`**, each immediately after `WaitSema(mcman_io_sema)`: `mc_open:318`, `mc_format:413`, `mc_remove:435`, `mc_mkdir:465`, `mc_rmdir:499`, `mc_dopen:521`, `mc_getstat:570`, `mc_chstat:594`, `mc_rename:688`, `mc_mount:753`, `mc_umount:771`. The resulting globals `mcman_mc_port`/`mcman_mc_slot` (`mcdev.c:15-16`) are the only port/slot the ops use. The remaining ops (`mc_close:353`, `mc_lseek`, `mc_read`, `mc_write`, `mc_dclose`, `mc_dread`) never call it — they act on `f->privdata`, the fd handle `McOpen` returned, whose port/slot were fixed at open time. `mc_ioctl`/`mc_devctl`/`mc_ioctl2`/`mc_chdir`/`mc_sync`/`mc_symlink`/`mc_readlink` ignore `f` entirely (already checked-clean, Round 3). **There is no devctl or side channel that presents a slot.**

Where `unit` comes from: `f->unit` of the iomanX file struct. The driver registers itself under the name `"vmc"` (`mcdev.c:105-114`, `BUILDING_VMCMAN` branch). That iomanX derives `unit` from the numeric suffix of the device name (`"vmc2:"` → unit 2) is PS2SDK iomanX behaviour, **not code in this repo — INFERRED** as a mechanism, but corroborated in-tree three ways: (i) `mc_open`'s own diagnostic prints `f->unit` next to the derived `mcman_mc_slot` (`mcdev.c:320-321`); (ii) EE code constructs exactly `"vmc%d:"` strings and passes them to `fileXioMount`/fileXio opens (B3); (iii) EE code parses `path[3] - '0'` back out of a `vmcN:` path as the slot index and range-checks it (B3).

### B3. Every in-tree EE flow addresses only vmc0:/vmc1: (READ)

- The mounted-state table itself is size 2: `int vmcMounted[2]` (`src/filer.c:60`, declared `include/launchelf.h:573`, `extern` in `src/dash_devices.c:21`). There is no storage in the EE program for a third VMC's state.
- The canonical mount entry **rejects any other slot**: `filerMountVmc`, `src/filer_browser.c:2347-2354` — `if (slot < 0 || slot > 1 || …) return -1;` then `sprintf(dev, "vmc%d:", slot)`. Its callers: the dashboard (`src/dash_browser.c:1217-1231` `opMountVmc`, invoked only as `opMountVmc(0)` / `opMountVmc(1)` at `:3006-3010`, menu entries literally "Mount as vmc0:"/"Mount as vmc1:" at `:2827-2828`) and the MMCE IGR helper (`src/mmce_igr.c:275,296,336` — `slot = !vmcMounted[0] ? 0 : (!vmcMounted[1] ? 1 : -1)`, aborting if both are taken). `filerUnmountVmc` has the same `slot > 1` rejection (`filer_browser.c:2397-2403`).
- The classic browser's inline mount path derives `i = ret - MOUNTVMC0` from a two-entry menu enum (`src/filer_browser.c:1501-1503`), so `i ∈ {0,1}`, then `fileXioMount("vmc%d:", …)` at `:1535`.
- Every device-enumeration loop is bounded at 2: dashboard device list `for (v = 0; v < 2; v++)` building `"vmc%d:/"` (`src/dash_browser.c:475-486`); `src/dash_devices.c:485-492` `for (i = 0; i < 2; i++)`; root listing adds only the literals `"vmc0:"`/`"vmc1:"` (`src/filer.c:2343-2348`); `unmountAll` writes `vmc_str[3] = '0' + i` for `i < 2` (`src/filer_mount.c:161-168`).
- Every *consumer-side* re-parse of a `vmcN:` path also gates at 2, so even a path string arriving from a config file, a clipboard, or a launch argument cannot smuggle a higher unit through Launchstation's own code: ELF launch `src/main_actions.c:369-373` (`x = path[3] - '0'; if ((x < 0) || (x > 1) || !vmcMounted[x]) goto ELFnotFound;`); clipboard source check `src/filer_browser.c:218-221` (`vmc_index < 2`); device-validity check `src/dash_devices.c:231-234` (only `vmc0:`/`vmc1:` literals recognised). All other `vmc` sites in `src/` are prefix tests (`strncmp(path, "vmc", 3)`) on paths the browser itself built from the enumerations above.
- Historical intent agrees: `docs/changes.txt:258` (READ) — "Note that **vmc0: and vmc1:** will not be shown in FileBrowser until some VMC file has been mounted" — the feature was designed as two slots.

- The only other in-tree consumer of the mcman **library** is `iop/smbd`, and it imports **xmcman** (the physical build), not vmcman (`iop/smbd/imports.lst:18-23`), always with slot 0 (`iop/smbd/smbd.c:213,217,227,229` — `McDetectCard2(port, 0)`, `McSetFileInfo(port, 0, …)`, `McGetCardSpec(share, 0, …)`).

### B5. Cost, restated with the backing array included (READ arithmetic)

- `mcman_vmc_cardinfo[MCMAN_MAXSLOT]`, `mciomanx_backing.c:26`: `vmc_cardinfo_t` = 24 B (**INFERRED** from the field layout at `mciomanx_backing.c:15-24` with normal 4-byte alignment) → 240 B vs 96 B (**−144 B**).
- **Total reclaimable at MAXSLOT=4: ≈33,984 B**, of which -085 already counted 33,840 B. (Not counted, and not part of the fix: `mcman_devinfos`' first dimension `[4]` — VMCMAN's port is always 0, but the physical build's `mcman_modloadcb` can produce ports 2–3, `mcdev.c:186-189`; that dimension is shared and out of -085's scope.)

### B6. Does dropping to 4 work with the mask? (READ arithmetic)

Yes — and it is precisely what makes the mask correct:

- VMCMAN at MAXSLOT=4: mask = `4 - 1` = 3 (`0b0011`), so `slot = unit & 3 ∈ {0,1,2,3}` — **contiguous and complete**: every slot in the tables is reachable, no slot is unreachable, units 0–3 map 1-to-1. Residual wrap (unit 4→0, 5→1, …) is the same inherent property every mask in this function has, including the physical build's, and no in-tree flow presents unit ≥ 2 anyway (B3).
- The physical (non-VMC, non-XFROM) branch, `mcdev.c:218-220`, at MAXSLOT=4 is already exact: `port = unit & 1`, `slot = (unit >> 1) & 3` maps units 0–7 onto all eight (port, slot) pairs uniquely, wrapping only at unit 8. The bug is not "masking" — it is that **10 is not a power of two, so `MAXSLOT-1` is not a mask at all**. At 4 the same expression is a true mask in both branches. XFROMMAN forces (0,0) (`:224-228`) and is unaffected.
- Honest bound: the in-tree evidence supports even MAXSLOT=2 (only slots 0–1 are ever used). **4 is still the right recommendation** — it is -085's own proposed value, it matches the physical build's slot width, and it keeps slots 2–3 addressable for a future 3rd/4th VMC without re-widening. Dropping to 2 would save a further ~5.3 KB but would silently cap the device at two VMCs forever; that trade is the maintainer's, and nothing in this section's evidence requires it.

**Settlement: -085 is CLOSED as proven waste. Slots 4–9 (indeed 2–9) are unpopulatable by any in-tree flow; slots 2–7 are unpopulatable by *any* device flow whatsoever. The fix is -085's: delete the `#ifdef BUILDING_VMCMAN` override at `mcman-internal.h:105-109` so both targets use 4 — a pure deletion that also fixes the mask (T1-F1).**

## (c) Mask verdict

**The mask is a latent live defect, not an intentional sparse map and not harmless dead generality.** No evidence of intent exists: no comment at `mcdev.c:221-223` or `mcman-internal.h:105-109`, no consumer of slots 8/9 (the only slots the mask adds over {0,1}) anywhere in-tree, the vmcman README's local-delta list never mentions the widening or a sparse scheme, and the feature's own documentation names only vmc0:/vmc1:. The expression is the power-of-two idiom applied to a non-power-of-two constant — an arithmetic accident introduced with the local 4→10 widening. Its failure mode is the worst kind: **silent aliasing**. A presented `vmc2:` does not error — it opens, reads, and *writes* slot 0's mounted image (units 2–7 → slots {0,1}); `vmc8:`/`vmc9:` would address slots that no in-tree mounter can ever have mounted, i.e. `mcman_devinfos[0][8]`/`[9]` state that is permanently unformatted. It is **latent, not live-in-tree**, for exactly one reason: every EE gate in B3 stops units above 1 before they reach the IOP. The device is registered globally with iomanX (`mcdev.c:262-277`, `mcman_initdev`), so the only thing standing between the aliasing and a wrong-card write is caller discipline in one EE program. Filed as T1-F1.

Interaction with -068 (not re-filed): -068's "currently unreachable" judgement for `slot == MCMAN_MAXSLOT` relied on this mask, and it **holds and is strengthened** — the mask bounds device-originated slots to {0,1,8,9} ⊂ [0,10), and B4 shows no other in-tree slot source. Note the judgement survives the -085 fix too: at MAXSLOT=4 the mask bounds slots to [0,4), so `slot == 4` remains unreachable from the device layer; -068's one-character validator fix is still worth doing on its own terms, but neither fix substitutes for the other.

## (d) Findings

### T1-F1 / VMCMAN unit→slot mask `unit & (MCMAN_MAXSLOT - 1)` is `unit & 9`: units 2–7 silently alias onto slots 0/1 and slots 2–7 are unreachable / Category 6 (latent)

- Locations: `iop/vmcman/src/mcdev.c:221-223` (VMCMAN branch of `mcman_unit2card`); constant at `iop/vmcman/src/mcman-internal.h:105-109` (`MCMAN_MAXSLOT` 10 under `BUILDING_VMCMAN`, 4 otherwise). All 11 call sites listed in §B2.
- Problem: `MAXSLOT - 1` = 9 (`0b1001`) is not a contiguous mask. Device units map only to slots {0,1,8,9} (§B1 table): a request for `vmc2:`–`vmc7:` is silently served by the card mounted as slot 0 or 1 — including writes, format, remove and mount/umount, since every op derives its slot here — and slots 2–7 of `mcman_fatcache`/`mcman_devinfos`/`mcman_vmc_cardinfo` can never be indexed from the device layer at all. Reachability today is blocked only by EE-side gates that cap every in-tree flow at slots 0–1 (§B3: `filerMountVmc`'s explicit `slot > 1` rejection at `src/filer_browser.c:2353`, launch/clipboard/validity gates at `src/main_actions.c:371`, `src/filer_browser.c:219-221`, `src/dash_devices.c:231-234`); the IOP device itself accepts any unit any EE caller presents. READ for the arithmetic, the call-site census and the EE gates; INFERRED that no out-of-tree EE client presents units 2–9 in the user's setup (none can be enumerated from this repo).
- Fix: Delete the `BUILDING_VMCMAN` override at `mcman-internal.h:105-109` so VMCMAN uses `MCMAN_MAXSLOT` 4 — the LAUNCHSTATION-085 fix. The mask becomes `unit & 3`, contiguous and complete (§B6); no line in `mcdev.c` changes. Do **not** "fix" the mask in isolation with `% MCMAN_MAXSLOT` while keeping 10: that keeps the ≈33.8 KB of dead statics and adds a division to a hot IOP path to preserve slots nothing populates.
- Benefit: Removes the silent wrong-card aliasing for units 2–7, makes every remaining slot reachable, and reclaims ≈33,984 B of IOP statics (§B5) — one deletion closes both this finding and -085.
- Effort: S (the edit is XS; S for the re-verification that no consumer regresses — this section is that verification for in-tree consumers)
- Risk: Low–Med — an out-of-tree consumer of slots 8/9 (the only mask-reachable slots being lost) would break; none exists in-tree (§B3/B4) and the feature's documentation has only ever promised vmc0:/vmc1: (`docs/changes.txt:258`).
- Confidence: READ (arithmetic, call sites, EE gates, absence of in-tree consumers); INFERRED only for out-of-tree consumers.

### T1-F2 / `mcman_iomanx_backing_mount` trusts its slot twice: cleanup runs `clear_slot` on slots the validator just rejected, and re-mounting overwrites a live fd / Category 6 (latent)

- Locations: `iop/vmcman/src/mciomanx_backing.c:60-159` — validator call at `:69`, unconditional-on-error cleanup at `:154-157` (`if (r < 0) mcman_iomanx_backing_clear_slot(slot);`), fd overwrite at `:84` (`cardinfo->fd = fd;`); `clear_slot` itself at `:28-40`. Sole caller: `mcdev.c:755` (`mc_mount`).
- Problem: Two distinct defects, neither covered by -068 (the validator's own `>` at `:46`) or -079 (geometry). (1) When `mcman_iomanx_backing_validate` rejects a slot > `MCMAN_MAXSLOT`, mount still falls into `cleanup:` and calls `clear_slot(slot)`, which dereferences `&mcman_vmc_cardinfo[slot]` out of bounds, conditionally `iomanX_close()`s whatever integer sits there as an "fd", `memset`s 24 bytes out of bounds, and calls `mcman_probePS2Card(0, slot)` into `mcman_devinfos[0][slot]`. The validator's rejection is thus immediately un-done by the error path — contrast `mcman_iomanx_backing_umount` (`:161-176`), whose cleanup does **not** call `clear_slot` on validation failure, and getcardspec/erase/write/read, which return before touching the array. (2) Mount is called with `check_mounted = 0` and never checks `cardinfo->mounted`: mounting an already-mounted slot overwrites `cardinfo->fd` at `:84`, leaking the previous iomanX fd permanently (and if the new image then fails validation, `clear_slot` wipes the slot, so the previously mounted card is lost as well as leaked). Reachability today: none in-tree — the sole caller's slot comes from the §B1 mask (≤ 9, always valid), and both EE mount paths unmount before mounting (`src/filer_browser.c:2355-2363`, `:1504-1512`). READ for all code paths; INFERRED/latent for reachability.
- Fix: (1) In `mc_mount`'s callee, only run the cleanup `clear_slot` when validation passed — e.g. initialise `r` from the validator and guard the cleanup with the validated range, mirroring `umount`'s shape; (2) at the top of mount, after validation, `if (cardinfo->mounted) mcman_iomanx_backing_clear_slot(slot);` before opening the new image — reusing the existing function, no new state.
- Justification: Fix (2) **adds** one call to an existing function; it is the smallest way to close an fd leak — the alternative (returning an error on re-mount) changes `mc_mount` semantics EE callers may rely on, and open-coding the close duplicates `clear_slot`.
- Benefit: A rejected slot can no longer cause an out-of-bounds write in the error path itself, and a re-mount can no longer leak an IOP file descriptor (a scarce, fixed-table resource) per occurrence.
- Effort: S
- Risk: Low — both changes are confined to paths that are erroneous or state-discarding today; the success path of a first mount is untouched.
- Confidence: READ (code paths and the umount contrast); INFERRED (latent reachability).

### T1-F3 / Backing read/write/erase never check `page` against the stored `cardsize`: writes and erases past the end of the image extend the backing file / Category 6 (latent)

- Locations: `iop/vmcman/src/mciomanx_backing.c:211-242` (erase), `:244-292` (write), `:294-371` (read) — each validates only the slot (`:218,251,301`), then seeks to `page * effective_page_size` and transfers, with no comparison against `cardinfo->cardsize`; the field is set at mount (`:87` comment "cardinfo->cardsize is total pages", assigned `:140`) and afterwards read **only** by `getcardspec` (`:195-197`). Dispatchers add no bound either: `McReadPage` (`iop/vmcman/src/main.c:1177-1192`, spot-READ) and the VMCMAN branch of `McWritePage` (`iop/vmcman/src/mcsio2.c:640`) forward `page` verbatim.
- Problem: For a mounted card, any page ≥ `cardsize` (or a page derived from corrupted geometry — the -079 territory upstream of this layer) seeks beyond the end of the image file the mount validator had just size-checked to the byte (`mciomanx_backing.c:117-124`). A read there fails short and returns 1 (benign). A write or erase there **extends the backing file** with a page of data/0xFF/0x00 at the wrong offset, silently changing the image's size so it no longer matches its own superblock — the exact invariant mount enforced — and a negative page produces a negative seek that fails cleanly (READ from the seek-error returns at `:235-238,266-269,323-326`). In-tree pages are geometry-derived, so reachability is via -079's crafted-image geometry or a direct export caller (-084's surface); filed separately because the bound belongs to this layer, which already stores the one number needed, and -079's fix (validating geometry at `mcman_setdevinfos`) does not bound direct page arguments.
- Fix: One comparison per function after validation, in the idiom the file already uses: `if ((u32)page >= (u32)cardinfo->cardsize) return 1;` in erase, write and read (3 lines, no new state, no signature change).
- Justification: The fix **adds** three one-line guards; justified because the value needed (`cardsize`, in total pages) is already stored per slot for exactly this card, no existing check anywhere in the dispatch chain supplies the bound (READ, §locations), and deletion/simplification cannot express a missing bound.
- Benefit: The backing layer can no longer grow or scribble outside the image it validated at mount, whatever geometry or caller produced the page number.
- Effort: S
- Risk: Low — legitimate pages are by construction `< cardsize` (total pages); a caller relying on past-end writes would already be corrupting its image.
- Confidence: READ (absent check, stored field, dispatcher behaviour); INFERRED (reachability — needs -079-class geometry or an out-of-tree export caller).

## (e) Checked and clean (READ, with citations)

- **All 11 `mcman_unit2card` call sites hold `mcman_io_sema`** — each is preceded by `WaitSema(mcman_io_sema)` in the same function (`mcdev.c:317/318, 412/413, 434/435, 464/465, 498/499, 520/521, 569/570, 593/594, 687/688, 752/753, 770/771`): the `mcman_mc_port`/`mcman_mc_slot` globals have no cross-op race from the device layer.
- **fd ops carry no slot risk**: `mc_close`/`mc_lseek`/`mc_read`/`mc_write`/`mc_dclose`/`mc_dread` (`mcdev.c:340-405,538-565`) use only `f->privdata`; port/slot live in the handle `McOpen` created.
- **`mc_chstat`'s VMCMAN full-info early return does not leak the semaphore**: it `SignalSema`s at `mcdev.c:622` before `return mcman_ioerrcode(r)` in the `MCMAN_ULE_FULL_INFO` (`0xFEED`) path (`:606-624`).
- **`mc_rename` name copy is bounded** (re-verified; Round 4 had it clean): length pre-checked against 20 (PS1) / `sizeof(mctbl.EntryName) - 1` (PS2) at `mcdev.c:695-698`, target `memset` to zero first at `:701`, so the `memcpy` at `:702` leaves a terminator.
- **Backing erase buffer is exactly sufficient**: `char buf[544]` (`mciomanx_backing.c:231`) vs maximum effective page size 544 = pagesize 528 (the largest mount admits, `:126-130`) + 16 ECC; the 512-page case writes 512 or 528. No overflow.
- **Backing read's software-ECC loop is bounded**: for pagesize ∈ {512, 528}, `ecc_count` = `pagesize >> 7` = 4 (`:345-349`), writing 4×3 = 12 bytes into the 16-byte ECC buffer pre-filled at `:338`; loop terminates via `i >= ecc_count`.
- **Backing getcardspec/erase/write/read and umount handle validation failure cleanly**: they return before dereferencing `mcman_vmc_cardinfo[slot]` (`:185-188,218-221,251-254,301-304`) and umount's cleanup does not call `clear_slot` (`:174-176`) — the contrast that isolates T1-F2 to mount.
