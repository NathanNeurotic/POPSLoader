# TASK 1 — The ds34 census

## Method

Copies were enumerated two independent ways: (1) filename search for `*ds34*` across all five trees; (2) a symbol net — grep for `hid_LEDRumble`, `PS4_11_REPORT_LEN` and `power_level` over every `.c`/`.h` in all five repos — which catches copies living under other filenames or with renamed functions (it caught RiptOPL pademu's renamed `hid_LEDRumbleCommand`, §1.4). Both nets return the same set: **10 IOP driver copies** — five Bluetooth (`ds34bt.c`) and five USB (`ds34usb.c`) — in three repos, plus EE client libraries that contain neither defect site (§1.5). PS2-Servers contains no ds34 code at all (PC server application). In every BT copy, `hid_LEDRumble` is the *only* builder of the DS4 output report (the remaining `PS4_11` references are the input-report dispatch), so the matrix below is complete for the defect, not sampled.

## Constants (identical in every copy's header — verified per file)

- `PS3_01_REPORT_LEN = 0x30` = **48** — e.g. Launchstation/iop/ds34bt/iop/ds34bt.h:247, POPSLoader/modules/pademu/ds34bt.h:227, RiptOPL/modules/ds34bt/iop/ds34bt.h:244.
- `PS4_11_REPORT_LEN = 0x4D` = **77** — e.g. Launchstation/iop/ds34bt/iop/ds34bt.h:251, POPSLoader/modules/ds34bt/iop/ds34bt.h:251, RiptOPL/modules/pademu/ds34bt.h:228.
- Every BT copy declares the report buffer as `u8 led_buf[PS4_11_REPORT_LEN + 2]` = **79 bytes**, starts `size = 2`, and in the DS4 branch does `size += PS4_11_REPORT_LEN` → **79 bytes transmitted** via `HID_command(...)`.
- The defect, in one line: the affected copies zero that buffer with the *DS3* length — `mips_memset(led_buf, 0, PS3_01_REPORT_LEN + 2)` = **50 bytes** — then assign only the DS4 header/LED/rumble fields (indices 0,1,2,4,7,8,9,10,11, and 12,13 when charging) and send all 79. **79 − 50 = 29 bytes of uninitialised IOP stack are transmitted to the controller on every DS4 LED/rumble update.**

## The census headline

**No copy in the family is correct on both defects.** The two reference fixes live in *different* lineages: POPSLoader's standalone BT copy is the only one that zeroes the full DS4 buffer (A2), and RiptOPL's pademu pair are the only ones that clamp the battery index (B9/B10). # TASK 2 — mcman / VMC geometry-validation comparison

## The three checks (defined once, from the Launchstation baseline)

LAUNCHSTATION-079/-080/-081 (round 4, cited here, not re-filed) established that Launchstation's IOP `vmcman` — vendored PS2SDK mcman plus local VMC deltas — trusts card-supplied data at three points:

- **Check A — geometry sanity before division/indexing.** `iop/vmcman/src/main.c:1391-1393` copies 0x150 bytes of page 0 over `MCDevInfo`'s geometry after only a magic check (:1383-1386) and a version-digit check (:1388-1389), overwriting the sane values `mcman_setdevspec` had just derived (:1334-1354). Sinks: division by `cluster_size >> 9` (:3791-3792, :3835), `%`/`/` by `clusters_per_block` (:1435, :1439), `pages_per_cluster` reads overrunning the 1,024-byte cache slots (:3766-3768), `pmce[16]` indexed by `cluster % clusters_per_block` (:3419, :3520-3524), `mcman_pagedata[32]` over-indexed (:52, :3543, :3553). The local VMC mount validator checks only magic, cardtype, `pagesize ∈ {512, 528}` and total file size (`iop/vmcman/src/mciomanx_backing.c:107-141`).
- **Check B — FAT index bounds.** `McGetFATentry`/`McSetFATentry` (`main.c:3905-3931`, :3872-3902) compute `ifc_index` from an unbounded `fat_index` and index `ifc_list[32]` (`mcman-internal.h:335`); card FAT chains feed the value (`McReadDirEntry` :3813-3828, `mcman_fatRseek` :1597-1643). A FAT entry of 0x01000000 yields `ifc_index` = 4096 — a read ~16 KB past the array.
- **Check C — name termination before string ops.** Card entry names (32 bytes, may be unterminated) reach `strlen`×3 in `mcman_getdirinfo` (`main.c:2041-2055`), `strcmp` (:1405, :1411, :2615), and an unbounded `strcpy` in `mcman_dread2` (`ps2mc_fio.c:283`, with the terminator written at :284 *after* the copy). The local delta D8 terminated only the *caller's* name copy (`ps2mc_fio.c:383-390`).

**Launchstation EE, Check A in detail** (`mcViewOpen`, src/mc_card_view.c:191-286): the image size itself must be an exact power-of-two MiB, raw or in the 528-byte ECC variant (:205-219); magic memcmp (:227); `page_size` must equal 512 and `pages_per_cluster` must equal 2, *exactly* (:232); `pages_per_block` must be nonzero and even (:233-235); `clusters_per_card × 2` must equal the file's actual page count — geometry cross-checked against the real file (:236-238); `first_allocatable` must be nonzero and `< clusters_per_card` (:239-241); `root_cluster` must be 0 (:243); and the allocatable range is taken as the *minimum* of three independent derivations under the comment "never trust a single field" (:249-261), with zero usable clusters a hard reject. No card-supplied value is ever used as a divisor: all strides are compile-time constants (512-byte pages, 1024-byte clusters, 256 FAT entries per cluster). Directory entry counts are capped at 4,096 (`MCV_MAX_SAVE_ENTRIES`, enforced at :293, :332, :389, :478), and the fingerprint walk carries a depth budget of 8 (:452) and a total-entry budget of 65,536 (:482).

**RiptOPL EE, Check A in detail** (`sysCheckVMCEx`, src/platform/sysvmc.cpp:138): two acceptance paths, both gated — the size-only path validates magic (27-byte memcmp), `mc_type == 2`, `page_size == 512`, `pages_per_cluster != 0`, and the geometry product against the real file size, widened to 64-bit before multiplying (:177-193, product at :190-191); the full-superblock path requires magic, `mc_type == 0x2`, `page_size != 0`, `pages_per_cluster != 0`, `clusters_per_card != 0`, and `(u64)size == (u64)pages_per_cluster × clusters_per_card × page_size` (:230-234), under a comment that names the threat model: "Widen before multiplying untrusted geometry." The `SYS_VMC_PROBE_FORMAT` path adds the strict form: `page_size == 512`, `pages_per_cluster == 2`, `pages_per_block` ≥ 2 and even (:236-238). Fields the EE never consumes (allocatable bounds, backup blocks, the indirect-FAT list) are not validated — correctly, because nothing downstream of the gate reads them from the image; they are interpreted later by game-side mcman over the emulated page interface.

## Verdicts per check

- **Check A (geometry): the strongest in-family implementations already exist — in two different shapes, each correct for its consumer.** For an *accept/reject gate* (does this image get used at all?), RiptOPL's `sysCheckVMCEx` product check is the model: one widened multiplication tying the header to the real file size catches the entire geometry class for the fields the gate's consumers use. For a *parser* (directory/FAT walking), Launchstation's own `mc_card_view.c` is the model: exact-value geometry, cross-checked against file size, allocatable range taken as the minimum of three derivations, and no card-supplied divisor anywhere. **The -079 fix should port the mc_card_view *shapes* into vmcman's `mcman_setdevinfos`** — same repo, same authorial idiom, no cross-repo dependency and nothing new to invent. (Round 4's filed -079 fix — compare the copied fields against the `mcman_setdevspec`-derived values — is the same destination by a shorter route; the two compose, they do not conflict.) **Do not port RiptOPL's gate into vmcman**: vmcman is a filesystem driver, not a gate; it must keep serving geometry the gate would reject outright (e.g. 528-byte-page physical cards), and its hole is *internal* trust of copied fields, not image acceptance.
- **Check B (FAT index): port the bound, not the code.** `mc_card_view.c`'s `fatGet` and vmcman's `McGetFATentry` solve the same double-indirect lookup with opposite discipline; the transferable content is three comparisons — double-indirect index `< 32`, indirect/FAT clusters `< clusters_per_card`, chain values `< alloc_usable` — which drop into `McGetFATentry`/`McSetFATentry` as the one-line guard -080 already specifies (`fat_index >= max_allocatable_clusters` → reject). No other repo has FAT code to port *from*: RiptOPL and POPSLoader have no in-repo FAT walker at all. **Verdict: cross-port the check shape from Launchstation's EE viewer to its own IOP driver; cross-repo, there is nothing to move.**
- **Check C (name termination): port the placement, not just the terminator.** The instructive difference is *where* the NUL is forced: vmcman's D8 fix terminated one caller's copy and left the search core exposed (-081); `mc_card_view.c` terminates inside `dirEntry`, the single helper every consumer passes through, so no call site can forget. **Verdict: adopt the helper-level placement in vmcman** (terminate where the entry is materialised, as -081's fix (a)/(b) does at the two consumption points — or better, at the one fill point both feed from); nothing to port cross-repo, since no other repo materialises card directory entries from an image.

**Task 2 headline:** the mcman validation gap is not a family-wide ignorance — it is a *placement* failure inside one repo. Launchstation contains both the family's worst card parser (its IOP vmcman: 0 of 3 checks, one partial) and its best (its EE viewer: 3 of 3, in the strongest forms found anywhere in the five repos), written against the same format description. RiptOPL independently built the family's best *gate*. Nobody lacked the knowledge; the checks were simply never carried across the EE/IOP boundary inside Launchstation, or across the gate/parser boundary anywhere.

- **Problem:** Two independent one-line defects, distributed across the family's ten ds34 driver copies with no copy free of both. (1) Four of the five Bluetooth copies zero the 79-byte DS4 output-report buffer with the 48-byte DS3 length (`PS3_01_REPORT_LEN + 2` = 50 of 79 bytes), then transmit all 79 bytes — 29 bytes of uninitialised IOP stack go to the controller on every DS4 LED/rumble update; the information content is whatever the IOP stack held, and the controller-visible symptom is garbage in report fields the driver believes it zeroed. ### X-51 / Rumble-strength scaling is split by lineage, not by repo: every pademu copy scales `rrum * 255`, every standalone copy passes it raw — in both transports, in both repos that carry pademu / Category 2

- **Locations:** Scaled: POPSLoader/modules/pademu/ds34bt.c:1188 (`led_buf[7] = rrum * 255`), RiptOPL/modules/pademu/ds34bt.c:1186; POPSLoader/modules/pademu/ds34usb.c:471, RiptOPL/modules/pademu/ds34usb.c:424 (`usb_buf[4] = rrum * 255`). Raw: Launchstation/iop/ds34bt/iop/ds34bt.c:1250, POPSLoader/modules/ds34bt/iop/ds34bt.c:1250, RiptOPL/modules/ds34bt/iop/ds34bt.c:1250 (`led_buf[7] = rrum`); Launchstation/iop/ds34usb/iop/ds34usb.c:438, POPSLoader/modules/ds34usb/iop/ds34usb.c:438, RiptOPL/modules/ds34usb/iop/ds34usb.c:586 (`usb_buf[4] = rrum`).
- **Problem:** The DS4 right-motor field receives two different interpretations of the same caller value depending on which lineage of driver a game/session happens to load: under pademu (in-game) the byte is scaled by 255 (so a caller's 1 becomes full-scale 255, and any value ≥ 2 wraps modulo 256 in the u8 field); under the standalone drivers the byte passes through (a caller's 1 is a barely-perceptible tremor). POPSLoader's round 3 recorded this as drift *inside* POPSLoader (in POPSLOADER-049's classification); the census shows it is systematic — the split follows the pademu/standalone fork exactly, across both transports and both repos carrying pademu copies, while Launchstation (standalone only) is uniformly raw. Which side matches the EE callers' contract is not determinable from the driver sources alone (INFERRED effect): the pademu callers pass pad-state bytes through the in-game padman emulation, the standalone callers through the EE libds34 API, and the two APIs may genuinely document different ranges — in which case each lineage is locally right and this is a trap for anyone who ports code between them, rather than a bug in either.
- **Fix:** No code change is proposed on this evidence. The LESS-NOT-MORE action is one sentence of documentation at each lineage's `LEDRumble`/`hid_LEDRumble`: state the expected range of `rrum` at that API boundary (0/1 flag vs 0–255 strength), so the divergence becomes a documented contract instead of silent drift. If the owner determines the contracts are in fact the same, the fix is deleting `* 255` (or adding it) in the two pademu lineages — four lines — and this finding is the map.
- **Benefit:** Prevents the next cross-lineage port from silently changing rumble behaviour; costs two comments.
- **Effort:** S. **Risk:** Low (documentation only, as filed). **Confidence:** High (READ) for the divergence itself — every site read in context this round; INFERRED for which side is behaviourally correct, stated openly above.
