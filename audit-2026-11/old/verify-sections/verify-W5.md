## Full reasoning — non-VERIFIED verdicts

### RIPTOPL-437 — VERIFIED-DRIFT

- **Claim re-derived:** In `DeviceReadSectors` (`modules/iopcore/cdvdman/device-smb.c:175-224`), for `NumParts > 1` each part covers `0x80000` sectors (`ubound` starts at `0x80000`, `:186`; loop `:191`). If `(u32)lsn` falls in no part's `[lbound, ubound)` window, no iteration body runs, nothing is read, and the function returns its initialised success value.
- **Drift:** the finding cites "`rv` initialised `SCECdErNO` at :182". In the pinned tree the declaration is `int rv = SCECdErNO;` at **`:180`** (function start `:175`, part loop `:191-221`, return `:223` — all as cited). Two-line drift only; no other cited line moves.
- **Caller check (no defeating guard found):** the ZSO cache caller `DeviceReadSectorsCached` (`modules/iopcore/cdvdman/cdvdman.c:396-415`) does now contain a fallback — if the wide `MAX_SECTOR_CACHE` window read fails it retries with just the requested sectors (`:400-406`). That fallback does **not** defeat the claim: it triggers only on a non-`SCECdErNO` return, and the defect is precisely that the past-the-last-part window read returns `SCECdErNO`, so the stale `sector_cache` window is installed (`cur_sector = lsn`, `:407`) and served by `memcpy` at `:410` as real data. The `mediaLsnCount` gate in `cdvdman_read` (`cdvdman.c:519-541`) does not cover this path either: `DeviceReadSectorsCached` is reached via `read_raw_data` (`cdvdman.c:429`), which has no `mediaLsnCount` check. Single-part images are unaffected (`ubound = 0xFFFFFFFF`, `device-smb.c:186`), as the finding states.

### RIPTOPL-439 — VERIFIED-DRIFT

- **Claim re-derived:** `sceCdStInit(u32 bufmax, u32 bankmax, void *iop_bufaddr)` (`modules/iopcore/cdvdman/streaming.c:122-142`) executes `StBanksize = bufmax / bankmax` at **`:132`** (exactly as cited) with no validation of either operand beforehand (`:126-133`). Both callers pass game-supplied values straight through with no guard: CDVDFSV `CDVD_ST_CMD_INIT` at `modules/iopcore/cdvdfsv/ncmd.c:267-268` and FILEIO `CDIOC_STREAMINIT` at `modules/iopcore/cdvdman/ioops.c:543-544`. `bankmax == 0` therefore divides by zero; `bankmax > bufmax` yields `StBanksize == 0`, and `AllocBank` (`streaming.c:145-160`) then keys purely off `StBanksize`, so the stall mechanism follows as described.
- **Drift:** the finding cites the `SteamingData` `unsigned short` fields at "`internal.h:84-96`". In the pinned tree `struct SteamingData` is at **`modules/iopcore/cdvdman/internal.h:69-81`** (`StBufmax`/`StBankmax`/`StBanksize`/`StWritePtr`/`StReadPtr`/`StStreamed` all `unsigned short int`, `:71-76`); lines 84-96 are the enclosing `cdvdman_status_t`. The truncation mechanism is in fact slightly stronger than stated: `StBankmax = bankmax` at `streaming.c:131` also truncates the `u32 bankmax` into the `u16` field before the division's result is stored.
