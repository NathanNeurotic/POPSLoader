## (b) Candidate findings (unnumbered)

### Candidate 1 — test_conformance.py locks in the empty-catalog run as a clean pass with "0 skipped", although the run skips every range check
- **Category:** 8 (test harness fidelity; round-8 hunt class 1 — a skip that reports as a pass)
- **Locations:** `RiptOPL/tools/pc/http/tests/test_conformance.py:40-46` (`test_empty_catalog_still_passes`); the behaviour it locks in is at `RiptOPL/tools/pc/http/http_conformance.py:219-222` (outside this batch, read for the cross-check)
- **Problem:** READ. For an empty catalog the tool prints "Range checks skipped." and "An empty catalog is valid, but it proves nothing about range support.", then returns 0 — and its summary line is built from counters that this path never increments (`res.skipped` is only bumped via `res.skip()`, used e.g. at http_conformance.py:272, not on the empty-catalog early return at :219-222). The test does not merely tolerate this: it asserts the exact summary string `"1 passed, 0 failed, 0 skipped"` and result 0 (:42-43), so the miscounted skip accounting is now the tested contract. A CI reader of the summary sees a fully-passing, nothing-skipped conformance run for a server about whose range support nothing was proven — the tool's own prose says so, its counters say the opposite, and the test sides with the counters.
- **Fix in words:** Make the empty-catalog path count the range section as skipped (route it through `res.skip()` like the other skips) and update the test to expect the honest summary (1 passed, 0 failed, N skipped) while keeping result 0 for the valid-empty-catalog decision itself.
- **Justification if the fix adds anything:** Adds nothing; it reuses the existing `res.skip()` counter and changes one expected string in the test.
- **Benefit:** The conformance summary can no longer present a run that exercised no range reads as a skip-free pass; the test stops encoding the miscount as correct.
- **Effort:** S / **Risk:** Low / **Confidence:** High on the test assertion and the counter mechanism (both READ); Med on calling result 0 itself wrong — the valid-empty decision is deliberate and is not challenged here, only the 0-skipped accounting.

### Candidate 2 — test_catalog_limits.py hard-codes HTTP_STREAM_ERR_TRUNC as -7 instead of extracting it like every other production constant it uses
- **Category:** 8 (test harness fidelity; round-8 hunt class 2 — staleness of a copied production value)
- **Locations:** `RiptOPL/tools/pc/http/tests/test_catalog_limits.py:37` (`#define HTTP_STREAM_ERR_TRUNC -7` in the generated harness preamble); production value at `RiptOPL/modules/network/common/httpclient.h:68` (`#define HTTP_STREAM_ERR_TRUNC -7`)
- **Problem:** READ. The file's whole method is to build the harness from *live* production text: the catalog limits and game constants are regex-extracted from `include/supportbase.h` / `include/httpsupport.h` at :40-43, and `httpParseCatalog` itself is extracted verbatim from `src/sources/httpsupport.cpp` at :48. The one exception is the error code the extracted function stores into `httpLastError` on the over-limit path: the harness predefines it as the literal -7 at :37, and the scenario-2 assertion (`httpLastError == HTTP_STREAM_ERR_TRUNC`, in the generated C main) compares the extracted code against the harness's own copy of the constant. The values agree today (-7 on both sides, verified), so nothing is currently broken — but if production ever renumbers the `HTTP_STREAM_ERR_*` values in httpclient.h, this test stays green while verifying the wrong number, because the extracted function is compiled against the copy, never against the header it ships with. It is the same silent-divergence shape as RIPTOPL-279's dedup cap, one constant wide.
- **Fix in words:** Derive the value the same way the neighbouring constants are derived — extract the `#define HTTP_STREAM_ERR_TRUNC` line from `modules/network/common/httpclient.h` into the generated preamble (failing loudly via the existing `extract()` RuntimeError if it disappears), and delete the hard-coded literal.
- **Justification if the fix adds anything:** Adds one extraction line and removes one literal; net neutral, no new machinery (the `extract()` helper already exists in the file).
- **Benefit:** The over-limit assertion verifies the production error code itself, so a future renumber is caught instead of silently ratified.
- **Effort:** S / **Risk:** Low / **Confidence:** High (both definitions and the extraction mechanism READ; the divergence is latent — the values currently match).
