## 3. Candidates

### L7-1 — `sha1.c` is an empty translation unit in the smbd build; delete its `ps2.yaml` line
- **Proposed Category:** 1 (dead code) · **Effort:** S · **Risk:** Low · **Confidence:** High
- **Mechanism / proof:** The entire body of `libsmb2/lib/sha1.c` (lines 43–450 of 450) sits inside `#if defined(USE_SHA1) && USE_SHA1` (`libsmb2/lib/sha1.c:43` … `#endif` :450). `libsmb2/lib/sha.h:6-8` defaults `USE_SHA1` to **0** when undefined. Nothing defines it to 1 for this build: not `iop/smbd/config.h` (read in full), not the smbd target's `defines`/`cflags` in `ps2.yaml` (read in full), and no header or source anywhere in the fetched tree contains a `USE_SHA1 1` definition (grep over the whole tree). Consistently, the SHA-1 dispatch cases in `libsmb2/lib/usha.c` are under the same guard and also compiled out, and no compiled caller references any `SHA1*` symbol. The object file therefore contains no code or data to reference or be referenced — the same source-level proof R4-R3(a) accepted for `quic.c`/`smbdirect.c`, and like those it does **not** depend on the missing link test.
- **Fix (LESS — pure deletion):** delete `.smbd-deps/libsmb2/lib/sha1.c` from the smbd sources (`ps2.yaml:317`). If a future re-pin enables SHA-1, the link fails loudly on `SHA1*` names and the line goes back.
- **Upstream status:** pristine upstream file; the deadness is created entirely by Launchstation's own build configuration, so the deletion is Launchstation's, not an upstream change.

### L7-2 — On PS2/IOP every "random" byte behind the NTLM server challenge, the preauth salt and the SMB3 seal nonce comes from a 15-bit LCG seeded with uptime-seconds ⊕ a constant ⊕ a heap pointer
- **Proposed Category:** 6 (defect, crypto) · **Effort:** M · **Risk:** Medium · **Confidence:** High on the mechanism (every link read); Medium on practical exploitation (state/seed recovery not executed here)
- **Mechanism, link by link (all READ):**
  1. `iop/smbd/config.h` defines **none** of `HAVE_ARC4RANDOM_BUF`, `HAVE_GETRANDOM`, `HAVE_DEV_URANDOM`. The only implementation of `smb2_random_bytes` that can run is therefore the fallback in `libsmb2/lib/init.c:400-410`: `p[i] = random() & 0xff;` per byte, returning **-1** to signal "fallback used".
  2. The IOP `random()` is `libsmb2/lib/compat.c:507-520` (compiled via config.h's `NEED_RANDOM`): a global LCG, `next = next * 1103515245 + 12345; return (next / 65536) % 32768;` — 15 bits of output per call, of which `& 0xff` keeps bits 16–23 of the state.
  3. The seed is set in `smb2_init_context` (`libsmb2/lib/init.c:427`): `srandom((unsigned)time(NULL) ^ getpid() ^ (unsigned)(uintptr_t)smb2);`. On IOP, `getpid()` is the constant **27** (`libsmb2/lib/compat.c:133-134`), `time()` is IOP system-clock seconds (`libsmb2/lib/compat.c:137-146`), and `smb2` is a heap allocation in the IOP's small address space. `srandom` (`compat.c:523-531`) writes the single process-global `next` (`compat.c:136`) — so **every new connection reseeds the one generator all contexts share**.
  4. Server reachability: `accept_cb` creates a fresh context per accepted connection via `smb2_init_context()` (`libsmb2/lib/libsmb2.c:5726`), consuming salt / client-challenge / GUID bytes from the sequence (`init.c:440-443`). The server session-setup path then generates the NTLM **server challenge** with `smb2_random_bytes(auth_data->server_challenge, 8)` (`libsmb2/lib/ntlmssp.c:1009-1010`) — directly under the file's own comment at :1004-1008: *"This has to be unpredictable: with a fixed challenge a captured response stays valid forever and responses can be precomputed offline."* The challenge is transmitted in cleartext, handing an attacker known outputs from the sequence. When a client negotiates SMB3 encryption, the same source produces the AES-CCM **nonce** at `libsmb2/lib/smb3-seal.c:155`, whose return value is ignored — directly under that file's own comment at :148-154: the nonce *"has to come from the strong source and not from random()"*. In this build it always comes from `random()`.
- **Consequence:** challenge freshness rests on at most the entropy of (uptime-seconds ⊕ a heap address), and the generator state is shared and reseeded per connection, so sequences repeat across sessions whenever seed inputs coincide. A predicted challenge defeats the anti-replay property NTLM challenge/response exists for; a predicted or repeated CCM nonce under one key breaks both confidentiality and integrity of sealed traffic (the seal file's own words). The upstream design anticipated this — the fallback is *signalled* (-1) — but no caller in the tree checks that return, and Launchstation's `config.h` selects no strong source.
- **Fix direction (for the parent to scope):** provide a real entropy source for the IOP build (or fail closed where `smb2_random_bytes` reports fallback for the challenge/nonce uses). Not a one-line deletion; filed as a defect of the *local copy as configured*, not of any single upstream function.
- **Upstream status:** all four files are pristine upstream; the defect is the composition — upstream fallback + upstream callers ignoring the fallback signal + Launchstation's `config.h` offering no strong source.

### L7-3 — Client async helpers leak their callback-data allocation when PDU creation fails (and on one validation return)
- **Proposed Category:** 6 (defect, leak) · **Effort:** S · **Risk:** Low · **Confidence:** High
- **Mechanism:** four sites allocate, then return without freeing on an error path that sibling functions in the same file handle correctly (e.g. echo/disconnect/copychunk paths all `free` on the same failure):
  - `libsmb2/lib/libsmb2.c:2046-2050` — `smb2_pread_async`: `rd = calloc(...)` (:2001), then `if (pdu == NULL) return -EINVAL;` — `rd` leaked.
  - `libsmb2/lib/libsmb2.c:2166-2170` — `smb2_pwrite_async`: identical shape, `wr` leaked.
  - `libsmb2/lib/libsmb2.c:3160-3164` — `smb2_ftruncate_async`: `if (pdu == NULL) return -ENOMEM;` — `create_data` leaked.
  - `libsmb2/lib/libsmb2.c:1409-1412` — `smb2_connect_share_async`: the `smb2->user == NULL` validation returns `-ENOMEM` without the `free_c_data(smb2, c_data)` every neighbouring failure branch performs — leaks `c_data` plus its `server`/`share` strdup's. Reachable when an application has cleared the user with `smb2_set_user(smb2, NULL)` (`libsmb2/lib/init.c:905-914` leaves `smb2->user` NULL in that case).
- **Consequence / reachability:** PDU creation fails under memory pressure, i.e. exactly when leaking is worst; each failed call leaks one small struct (plus two strings at the fourth site). **Client-only:** no server caller exists for any of the four functions (§2), so in the shipped `smbd.irx` these sections are GC candidates, not live code. Filed against the local copy as upstream-client defects, with that reachability stated.
- **Upstream status:** pristine upstream.

### L7-4 — File-notify list is freed by recursion whose depth is set by the remote server's reply
- **Proposed Category:** 6 (defect, stack) · **Effort:** S · **Risk:** Low · **Confidence:** Medium
- **Mechanism:** `libsmb2/lib/libsmb2.c:4245-4252` — `free_smb2_file_notify_change_information` frees the list by recursing on `fnc->next` before freeing the node. The list is built by `smb2_decode_filenotifychangeinformation` (`libsmb2.c:4198-4244`) with one heap node per entry in a **server-supplied** change-notify buffer; the decoder's own checks bound each entry to ≥12 bytes and the walk to the buffer, so the node count — and therefore the recursion depth when the list is freed (callers: `libsmb2.c:4322-4325` on decode error, and `libsmb2/lib/sync.c:1165` for the synchronous API's result) — is `reply_length / 12`, with `reply_length` taken from the reply (`rep->output_buffer_length`), not from the 4,096-byte request size the PS2 client asks for (`libsmb2.c:116-117`). A malicious or broken server can therefore drive thousands of nested frames on the freeing thread's stack; decode itself is iterative and safe.
- **Reachability:** client-only (change-notify client API; smbd's server-side notify is a different path in `smbd_fs.c`). In the shipped server build this is a GC candidate (§2). The defect is real in the local copy for any PS2 *client* use of the fetched library.
- **Fix shape:** iterative free (walk-and-free), a few lines.
- **Upstream status:** pristine upstream.

### L7-5 — AES-CCM tag verification uses early-exit `memcmp` on unauthenticated data
- **Proposed Category:** 6 (defect, crypto hygiene) · **Effort:** S · **Risk:** Low · **Confidence:** Medium on the mechanism; Low on practical exploitability
- **Mechanism:** `libsmb2/lib/aes128ccm.c:174-190` — `aes128ccm_decrypt` first decrypts the payload in place (:183), then computes the expected tag and finishes with `return memcmp(tmp, m, mlen);` (:189). `memcmp` returns at the first differing byte, so verification time leaks the position of the first tag mismatch. The sole caller, `smb3_do_decrypt_pdu` (`libsmb2/lib/smb3-seal.c:211-216`), does check the result and refuses the PDU, so no unauthenticated plaintext is *consumed* — the residual issue is purely the timing oracle on a 16-byte tag, over a LAN, against an IOP: filed for completeness with exploitability explicitly doubted, not as a practical forgery route.
- **Fix shape:** constant-time compare of the 16 tag bytes before returning.
- **Upstream status:** pristine upstream (non-OpenSSL body; the OpenSSL body at :192ff delegates tag checking to EVP and is not compiled here).

## 4. Checked-clean / dissolved candidates (with reasoning)

- **asn1-ber decode internals — clean.** `asn1ber_length_from_ber` (`libsmb2/lib/asn1-ber.c:127-183`) rejects long-form counts >4 and, critically, rejects any decoded length exceeding the bytes actually remaining in the source buffer (:171-180). `asn1ber_next_byte` (:64) bounds-checks every byte, so the integer decoders (:273/:349/:415/:490), which read their length as a single raw byte and therefore reject every long-form encoding outright (any `0x80|n` value exceeds their 4/8-byte caps), cannot read out of bounds. `asn1ber_oid_from_ber` (:550-636) caps content length at `BER_MAX_OID_ELEMENTS` (32), bounds element writes by `i < BER_MAX_OID_ELEMENTS`, and rejects trailing content; a sub-identifier encoded with excessive continuation bytes wraps a `uint32_t` (defined unsigned behaviour) and yields a garbage OID that simply fails the caller's comparison — no memory effect. `asn1ber_bytes_from_ber` (:637) rejects `vallen > maxlen` before copying. Encode side: `asn1ber_annotate_length`'s memmove arithmetic (:95-125) was verified (destination = `out_pos + lenbytes`, length = content bytes, both bounded by the earlier bounds-checked writes); the two `reserve = 1` call sites in `spnego-wrapper.c` (:321, :330) wrap contents of 3 bytes and a short OID respectively, so the 1-byte length reservation is provably sufficient there. BER indefinite length (`0x80`) is treated as length 0 by `asn1ber_length_from_ber` — a conformance wart that desynchronises parsing of such tokens toward rejection, with no unsafe read; not filed.
- **`compat.c` `poll()` FD_SET without an fd-range check — dissolved.** The unbounded `FD_SET(fds[i].fd, …)` (`compat.c:675-689`) looks exposed, but its only server-build callers pass a single descriptor that is already validated: the listener in `libsmb2/lib/socket.c:2018-2022` (guarded by `SMB2_VALID_SOCKET`, and the accept path in the same file rejects `clientfd >= FD_SETSIZE`), and the connection fd in client `sync.c`. No wire-controlled value can become an fd here.
- **`compat.c` `gethostname` — dissolved.** `strncpy(name, "PS2", len)` (`compat.c:126-130`) never NUL-terminates if `len < 4`, but its sole compiled caller passes `sizeof(server->hostname)` (`libsmb2/lib/libsmb2.c:5773`), far larger than 4.
- **`compat.c` `time()` ignoring its `tloc` argument — dissolved for this build.** `compat.c:137-146` returns the time but never stores through `tloc`, a real POSIX-contract violation in the abstract. Its only address-taking caller in the tree is `time(&now)` at `libsmb2/lib/libsmb2.c:5959`, which sits inside `#ifdef HAVE_LIBKRB5` — not defined by `config.h` or the smbd defines — so the uninitialised-read path is **compiled out** of smbd. Every compiled caller uses `time(NULL)`. Latent upstream issue, not a defect of the shipped module; recorded so a future krb5-enabled build re-checks it.
- **`compat.c` IOP `asprintf` two-pass `prnt` walk — clean at its call sites.** `compat.c:167-186` counts with a first `prnt` pass, allocates `len + 1`, and re-runs `prnt` writing through `prnt_char` (:154-165), which has no per-write bound check. The two passes format the same argument list deterministically, so the second pass cannot produce more characters than were counted; the only compiled caller formats `"\\\\%s\\%s"` with two strings (`libsmb2/lib/libsmb2.c:1415`). No overflow mechanism at any in-build call site.
- **`compat.c` `writev`/`readv` — clean.** Both carry an explicit total-length overflow guard (`compat.c:558-565`, :601-609) and bound their scatter/gather copies by the running remainder / actual bytes read; totals at call sites are PDU-sized (receive cap chain settled in R4-R2).
- **`compat.c` `strdup` int length — dissolved.** `len = strlen(s) + 1` in an `int` (`compat.c:756-774`) wraps only for strings over 2 GiB; no such string can exist in the IOP module.
- **`md4c.c` / `md5.c` — clean.** Stock RSA Data Security reference code. Partial-block arithmetic verified line by line: `MD5Update` (`libsmb2/lib/md5.c:72-106`) keeps the fill level in 1..64 and never copies past the 64-byte block; `MD4Update` (`libsmb2/lib/md4c.c:109-142`) derives `index`/`partLen` from the bit counter consistently; both length counters carry into the high word correctly. All call-site inputs are session/auth blobs, far below any counter limit.
- **SHA family — clean where live, dead where not.** SHA-256 (`libsmb2/lib/sha224-256.c`) and SHA-512 (`libsmb2/lib/sha384-512.c`) are stock RFC 4634: the `AddLength` macros set `Corrupted` on total-length overflow, `Input` loops are byte-wise with the block index reset inside `ProcessMessageBlock`, and padding writes stay inside the block buffer. Message lengths in this build are bounded by the PDU receive cap. SHA-1 is compiled out entirely (L7-1) and SHA-224's section of `sha224-256.c` is under the identical dead guard (`USE_SHA224` defaults to 0, `libsmb2/lib/sha.h:10-12`) — a GC-handled section of a live TU, not a separate deletion. `usha.c` dispatch for the dead variants returns `shaBadParam`, which is the correct behaviour.
- **`hmac.c` / `hmac-md5.c` — clean.** Keys longer than the block size are hashed first (`libsmb2/lib/hmac.c:106-116`; `libsmb2/lib/hmac-md5.c:35-44`); pad construction loops are bounded by `blocksize` (≤128) against arrays sized `USHA_Max_Message_Block_Size` (=128, `libsmb2/lib/sha.h:100`, :238) and 65 bytes respectively (64-byte MD5 pads + terminator room). All in-build keys are 16–32 bytes.
- **`aes.c` / `aes_reference.c` — clean (live path).** Stock tiny-AES: key expansion writes exactly `Nb*(Nr+1)*4 = 176` bytes into a 176-byte round-key buffer; `smb2_Cipher`/`smb2_InvCipher` round counts and state indexing are the reference implementation's. The CBC pair and ECB-decrypt exports are unreferenced in the compiled set (grep-verified) — already recorded in R4 and, per the settled revision, **not** refiled here.
- **`aes128ccm.c` length encodings — clean at the only call site.** `aes_ccm_generate_b0` truncates `plen` to 32 bits (:54-55) and the AAD length to a 16-bit CCM encoding (:84), both wrong for gigantic inputs in the abstract; the sole compiled caller (`libsmb2/lib/smb3-seal.c:182-186`, :211-212) always passes `alen = 32` and `plen` bounded by the PDU caps, and the counter-block layout matches `L' = 3` for the 11-byte nonce used. No reachable truncation.
- **`smb2-signing.c` — clean; one dissolved sub-lead.** Portable AES-CMAC (`smb3_aes_cmac_128`, :318-365) was verified for the empty-message (`n`→1, `rem` 0, subkey-2 padding), complete-block, and partial-block cases against RFC 4493. `smb2_calc_signature`'s gather-into-one-buffer path (:438-468) allocates the summed iovec length, which is ≥64 whenever reached via `smb2_pdu_add_signature` (which pre-checks `niov ≥ 2` and a 64-byte first vector, :505-513) and PDU-bounded in general. **Dissolved:** `smb2_pdu_check_signature` (:542-548) is a stub that returns 0 unconditionally — alarming in isolation, but it has **no caller anywhere in the compiled set** (grep-verified); actual inbound verification is performed inline with `smb2_calc_signature` + `memcmp` in `libsmb2/lib/socket.c:1188-1215` (including the strip-the-SIGNED-flag case) and `libsmb2/lib/libsmb2.c:1001-1019`. Recorded as a dead stub in a live TU (inventory), not as a verification bypass.
- **`smb2_kdf` / `smb2_create_signing_key` (libsmb2.c:718-870) — clean.** The KDF's 32-byte `input_key` buffer is safe because every caller clamps `ki_len` (16 from `smb2_derive_key`; `MIN(session_key_size, SMB2_ENC_KEY_SIZE_MAX)` on the 3.1.1 path) and the copy is `MIN(ki_len, derivation_key_len)`. The 2.x signing-key copy and the zero-key comparison read exactly 16 bytes from `smb2->session_key`, which the only compiled producer, `ntlmssp_get_session_key`, always allocates at exactly `SMB2_KEY_SIZE` (`libsmb2/lib/ntlmssp.c:1509-1516`); the variable-length krb5 producer is not compiled.
- **`decode_dirents` (libsmb2.c:381-453) — clean.** The walk the round-3/4-era code left exposed is now guarded in this pin: `next_entry_offset` must be non-regressing and in-buffer (:438-447 region: `fs.next_entry_offset > vec->len - offset` rejected), each entry is decoded from a fresh zeroed struct, and entries are list-owned from allocation, so the error path frees them via `free_smb2dir`.
- **`smb2_lseek` SEEK_CUR/SEEK_END negative-offset checks — dissolved.** `fh->offset` and `end_of_file` are `int64_t` (`libsmb2/lib/libsmb2.c:176-177`), so `fh->offset + offset < 0` is a meaningful signed test; it is only technically UB within one of `INT64_MAX` of the limit, a value only a local API caller — never the wire — can supply.
- **`smb2_server_side_copy_async` calloc/memcpy size wrap — dissolved (distinct from settled R4-R1).** `calloc(chunk_count, sizeof(struct smb2_srv_copychunk))` (`libsmb2.c:3945-3946`) followed by `memcpy(..., chunk_count * sizeof(...))` (:3953-3954) precedes the count guard in `smb2_encode_copychunk_input` (:3718), which invites a second look. On 32-bit the allocation size and the memcpy size are the *same* product computed in the *same* width, so they wrap identically and the copy cannot overrun the allocation; the allocation's NULL case is checked (:3947-3951). On 64-bit neither wraps. The downstream guard then rejects oversize counts before anything reaches the wire. No overflow mechanism survives the arithmetic.
- **`smb3-seal.c` encrypt-side length sum — clean.** `spl` (`libsmb2/lib/smb3-seal.c:136-146`) sums locally generated iovec lengths into a `uint32_t` and `calloc`s the result with a NULL check; server replies are bounded by the negotiated sizes and the R4-R2 receive-cap chain, orders of magnitude below wrap.
