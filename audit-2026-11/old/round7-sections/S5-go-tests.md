## 2. Candidate findings

### S5-01 / No test anywhere exercises a real `ServiceLogs` manager — PS2SERVERS-068 is untestable by the suite as written, and its fake deletes the argument that matters
- **Category:** Test coverage (known-bug hole)
- **Locations:** `internal/webui/webui_test.go:551` (`fakeManager.ServiceLogs`); the only log-endpoint tests at `webui_test.go:555` (`TestLogsIncludeTheServersOwnOutput`), `:580`, `:598`, `:613`. Absence verified by grep: **zero** occurrences of `openwrtManager`, `systemdManager`, `clampLogLines`, `maxServiceLogLines`, `logread` or `journalctl` in any `*_test.go` in the module. The defect itself: `internal/webui/service.go:173-177` (`openwrtManager.ServiceLogs(lines int)` never uses `lines`); the honouring contrast at `service.go:208-213`.
- **Problem:** PS2SERVERS-068 is not merely un-covered, it is *un-coverable* by the existing tests. `fakeManager.ServiceLogs(int) ([]string, error) { return m.logs, m.err }` discards its parameter by construction, so `HandleLogs` could pass 0, 5 or 1,000,000 and every log test would behave identically; and `testAPI` (`webui_test.go:22`) never even sets `API.logLines`, so the value flowing from `api.go:284` (`a.manager.ServiceLogs(a.logLines)`) is the zero value throughout. The three `HandleLogs` tests assert presence of lines, the "service logs unavailable" marker, and SSE-injection resistance — never a **count**. So the suite does **not** assert the unclamped behaviour (no test encodes the bug); it simply has no observation point where the bug could appear. Round 5 had to build an out-of-tree rig with a fake `logread` on `PATH` to demonstrate 068 at all — that rig was never committed as a test.
- **Fix (LESS NOT MORE):** One test, in `webui`: fake `logread`/`journalctl` executables on `PATH` (the round-5 rig, ~40 lines) asserting `openwrtManager.ServiceLogs(5)` and `systemdManager.ServiceLogs(5)` each return exactly 5 lines from a 2,000-line source, plus a `clampLogLines` table test (0→100, 501→500, 5→5) — the helper is six lines and currently has no direct test either. No production change.
- **Benefit:** The documented 500-line memory bound on the memory-constrained platform becomes regression-guarded instead of asserted only in a comment (`service.go:67`).
- **Effort:** S · **Risk:** Low · **Confidence:** High (READ — absence is grep-verified across the whole module; the fake's discarded parameter is definitional)

### S5-02 / PS2SERVERS-069: `uciBool` is tested in isolation while the `Load` switch that bypasses it has no test at all — the helper test certifies a path the config never takes
- **Category:** Test coverage (known-bug hole; false confidence)
- **Locations:** `internal/webui/webui_test.go:707-718` (`TestUCIBoolMatchesOpenWrtTrueValues`); the bypassed call sites in shipped code at `internal/webui/config_uci.go:81` (`main.read_only`), `:125` (`smb.read_only`), `:149` (`udpbd.read_only`) and the other thirteen narrow `val == "1" || val == "true"` expressions in the same `Load` switch, against the sole `uciBool` use for `main.udp_batch` (`config_uci.go:89`). Absence verified by grep: no test references `uciBackend`, the UCI `Load`, or the UCI `Save` — the only backend `Load` tested is the JSON one (`webui_test.go:91`).
- **Problem:** Both halves of the task's question land on the bad side, with one precision: **no test asserts that `read_only 'on'` loads as false** (nothing encodes the bug as expected behaviour), but **no test covers the load path or the save-strips-protection path either**. The single UCI test proves the *helper* accepts `1/true/on/yes/enabled` and rejects `0/false/off/no/disabled/""` — exactly the vocabulary the sixteen real keys do **not** use. A reader of the suite reasonably concludes "UCI booleans are tested"; the thing tested is the one key that was already correct. The dangerous sequence in 069 — hand-edited `read_only 'on'` → dashboard `Load` reads `false` → unrelated dashboard `Save` writes `'0'` — involves two functions (`uciBackend.Load`, `uciBackend.Save`) with zero tests between them, partly because `Load` shells to `/sbin/uci`, which does not exist in CI either (round 5, §5) — i.e. the current design is untestable as written, which is itself the finding.
- **Fix (LESS NOT MORE):** When 069 is fixed (use `uciBool` at all sixteen sites), extract the per-key parse switch from the `uci` exec — or inject the command runner — and add one table test over the raw pairs `Load` receives: for each of the three `read_only` keys and one `enabled` key, `on/yes/enabled/TRUE` → `true`, then a Load→Save round-trip asserting the emitted value stays `1`. Until the fix, that test is the executable statement of 069. No new helper; the seam is the one `Load` already needs.
- **Benefit:** Closes the only security-direction hole in the suite (a fail-open protection silently removed by an unrelated save) and removes a test that currently argues, falsely, that the area is covered.
- **Effort:** S (test alone) / M (if the exec seam must be extracted first) · **Risk:** Low · **Confidence:** High (READ)

### S5-03 / `tryTrans2` cannot fail: it returns `nil` unconditionally and calls the helper that already `Fatal`s — its callers' error branches are dead code
- **Category:** Vacuous / misleading test helper
- **Locations:** `internal/smb/integration_test.go:65-70` (definition and its comment); sole callers at `internal/smb/limits_test.go:84` and `:89` (both inside `TestSearchesAreBounded`). The wrapped function: `internal/smb/integration_test.go:156-196` (`trans2`), whose status check `Fatal`s at `:175-177`.
- **Problem:** The comment promises "`trans2` without the `t.Fatal`, for tests that drive it in a loop". The body does the opposite of the promise: it calls `cl.trans2(...)` — which `Fatal`s on any non-success status — and then returns `nil` as its error, always. So (a) the helper's stated purpose (letting a loop continue past a failure and inspect it) is impossible; (b) both call sites guard with `if _, _, err := cl.tryTrans2(...); err != nil { t.Fatalf(...) }`, a branch that can never execute; and (c) a future caller trusting the signature will write error handling that silently never runs. This is the suite's one literal "error return ignored / failure path that cannot fire" defect, in helper form.
- **Fix (LESS NOT MORE):** Delete `tryTrans2` (6 lines) and call `cl.trans2` directly at the two sites, dropping the dead `err` checks — the behaviour today is already exactly that. Net −10 lines, no behaviour change. (If a non-fatal variant is genuinely wanted later, it must be built on `call`, not on `trans2`.)
- **Benefit:** Removes a trap for the next limits test and makes `TestSearchesAreBounded` read as what it is.
- **Effort:** S · **Risk:** Low · **Confidence:** High (READ — definitional)

### S5-04 / The three SMB "bounded" tests assert no bound: searches, open handles and trees are checked only for "the server still answers / still returns SUCCESS"
- **Category:** Vacuous oracle (named behaviour unobserved)
- **Locations:** `internal/smb/limits_test.go:63-93` (`TestSearchesAreBounded`), `:94-110` (`TestOpenHandlesAreBounded`), `:111-130` (`TestTreesAreBounded`). The bounds they name: `internal/smb/wire.go:138` (`MaxSearches = 16`), `:141` (`MaxOpenFiles = 64`), `:143` (`MaxTrees = 16`), enforced by `evictOldest` at `handlers.go:729`, `:229`/`:367`, `:170`.
- **Problem:** Each test's own header comment states a memory defect (2000 searches ≈ 80 MiB of heap; unbounded handles exhaust FDs; unbounded trees ≈ 32 MiB across 16 connections) and each test then asserts something an **unbounded** implementation also satisfies at the chosen scale:
  - *Searches:* 128 × FIND_FIRST2 over a 40-file share, then one more, asserting only that a reply arrives (`:84-92`, via the dead-error helper of S5-03). An unbounded server holds 129 small listings in memory and answers identically. Nothing inspects a count, a heap, or an eviction.
  - *Trees:* 128 × TREE_CONNECT asserting `StatusSuccess` each time (`:124-129` in file numbering `:111`ff.). An unbounded server also returns SUCCESS 128 times; the allocation the comment fears is never measured.
  - *Open handles:* 256 × OPEN asserting SUCCESS (`MaxOpenFiles*4`). This one can only fail if the process actually runs out of file descriptors — at 256 opens, under any ordinary CI `ulimit -n` (≥1024), an unbounded server passes too. **INFERRED** for the FD ceiling specifically; definitional for searches/trees.
  Contrast within the same repo: `internal/sessionstats/sessionstats_test.go:69` `TestClientsAreKeptApartAndBounded` asserts the bound directly (`Active() != 2` fails, and the evicted client's line is checked) — the pattern these three needed already exists in the codebase. Because these tests are in package `smb`, the connection's `searches`/`files`/`trees` maps are reachable from the test if a handle to the connection is exposed, or the counts can be asserted through the same eviction side-effects sessionstats uses.
- **Fix (LESS NOT MORE):** Add one direct assertion per test — the live count never exceeds the `Max*` constant (or: the oldest search/handle/tree is the one evicted, mirroring sessionstats). No new framework; three assertions in three existing tests. Delete nothing.
- **Benefit:** Converts three regression guards that currently guard only against a crash/hang into guards against the memory defects their comments describe — the defects that matter on a 32 MB board.
- **Effort:** S · **Risk:** Low · **Confidence:** High (READ) for searches/trees; Medium (INFERRED, FD-limit-dependent) for open handles

### S5-05 / `TestUnsolicitedWriteRDMAIsIgnored` verifies the wrong sector: a guard failure writes at offset 0, and the test only ever reads sectors 600–601
- **Category:** Wrong oracle
- **Locations:** `internal/udpbd/udpbd_test.go:348-365`. The guarded path (context, not re-audited): `internal/udpbd/server.go:471-485` — with no CMD_WRITE handshake, `s.write` is the zero `writeState`, whose `offset` is `0`; the drop is the `st.left <= 0 || !peerMatch` check at `:476`.
- **Problem:** The test sends an unsolicited WRITE_RDMA full of `0xCD`, then proves innocence by reading **sectors 600–601** and comparing them to the image (`udpbd_test.go:361-364`). Nothing in the test reads sector 0, compares the whole image, or checks any sector the packet could actually have written. Trace the mutation the test exists to catch — the handshake guard removed or inverted: `handleWriteRDMA` proceeds with `st.offset == 0`, `size` from the packet's own block type, and writes the `0xCD` payload at **offset 0**. Sectors 600–601 are untouched, `readSectors(..., 600, 2)` matches the image, and the test **passes on the corrupting code**. The sibling test `TestTruncatedWriteRDMAIsIgnored` (:369) does this correctly — it initiates the write at sector 400 and reads sector 400 back — which is the proof the 600 choice is an error rather than a convention. (Why 600? **INFERRED:** it appears to be an arbitrary "somewhere else" sector; no state in the test ever points the write machinery at 600.)
- **Fix (LESS NOT MORE):** Change the verification read from sector 600 to sector 0 (one number), or — stronger for the same lines — compare the whole 1 MiB image after the packet, as `TestBlockWriteCannotExceedItsDeclaredSectorCount` does in udpfs. No new test.
- **Benefit:** The test starts catching the exact silent-corruption regression its header comment describes.
- **Effort:** S · **Risk:** Low · **Confidence:** High (READ — offset is the zero value by construction, traced above; not executed, no Go toolchain in this VM)

### S5-06 / `TestInfoResetsStaleWriteState` never tests the reset: it checks that a later read has the right length, which passes whether or not INFO cleared anything
- **Category:** Vacuous oracle (named behaviour unobserved)
- **Locations:** `internal/udpbd/udpbd_test.go:466-489`. The behaviour named: `internal/udpbd/server.go:353` (`handleInfo` sets `s.write = writeState{}`).
- **Problem:** The test initiates a write (CMD_WRITE, sector 10, 2 sectors), sends CMD_INFO, receives its reply, then reads one sector and asserts only `len(got) != SectorSize` fails (`:485-488`) — not the bytes, and not the write state. A server in which INFO did **not** reset the write state answers that read identically: reads do not consult `s.write`. The observable consequence of a stale state — a subsequent WRITE_RDMA with the pre-INFO cmdid completing the abandoned 2-sector write at sector 10 — is never sent. So the one behaviour in the test's name has no failure path. It is also the only content-free read assertion in the file: every other `readSectors` call site byte-compares against the image.
- **Fix (LESS NOT MORE):** After the INFO, replay the pending WRITE_RDMA for the abandoned write and assert sector 10 still holds the image bytes (the S5-05-corrected unsolicited case, reused), and byte-compare the existing read. ~6 lines added to the existing test.
- **Benefit:** The rediscovery/reset path — the same handoff family the udpfs rediscovery tests pin so carefully — gets an actual guard in udpbd.
- **Effort:** S · **Risk:** Low · **Confidence:** High (READ)

### S5-07 / `TestServerPortFallback` asserts no port: the fallback it is named for could be deleted and the test would still pass
- **Category:** Vacuous oracle (named behaviour unobserved)
- **Locations:** `internal/webui/webui_test.go:638-668`. The behaviour named: `internal/webui/webui.go:238-266` — `Port > 0` binds it; `Port == 0` tries `DefaultPort` (8082, `webui.go:20`), and on failure falls back to an ephemeral port.
- **Problem:** The test constructs `Config{Port: 0}` (comment: "trigger default / fallback logic"), sleeps 100 ms, cancels, and asserts only that `Serve` returned `nil`. It never dials the server, never reads a bound address, and never occupies 8082 to force the second branch. Mutations that pass it unchanged: bind a random port immediately (fallback-to-default deleted), bind 9999, or ignore `Port` entirely. What it actually proves — `New` succeeds on loopback and `Serve` shuts down cleanly on cancel — is already proved by implication in other tests and is not what its name claims. It is also the suite's only sleep-based test (`time.Sleep(100ms)`, :661) with no synchronisation on the thing slept for.
- **Fix (LESS NOT MORE):** Assert the observable: with `Port: 0` and 8082 free, an HTTP GET to `127.0.0.1:8082` answers; then, with 8082 occupied by a test listener, `Serve` still starts (ephemeral branch) — or, if the bound port is not exposable, rename the test to what it proves (`TestServeStartsAndStopsCleanly`) so nobody trusts it as fallback coverage. Deleting the name's promise is preferable to keeping a false one.

### S5-09 / The 32-bit wrap regression test never runs on a 32-bit target in CI, where its own comment says is the only place it is meaningful
- **Category:** Environment-gated test, never run in the configuration it guards
- **Locations:** `internal/smb/limits_test.go:17-61` (`TestReadCountCannotWrapNegative`); its own caveat at `:29-33` ("meaningful on 64-bit only as a clamp check"). CI: `edge.yml` test job is `ubuntu-latest` with the default amd64 toolchain; `edge-build.yml` builds `windows-386` and other 32-bit targets but runs no tests on or for them; no workflow sets `GOARCH=386` for a test step (grep-verified across `.github/workflows/`).
- **Problem:** The defect was an `int` sign-wrap that exists only when `int` is 32 bits — i.e. on mipsle/mips/arm/386, "every small target this build exists for" (test comment). On the amd64 CI runner the arithmetic cannot wrap, so the test exercises only the downstream clamp; a regression that reintroduced a wrap *without* breaking the 64-bit clamp (e.g. a differently-shaped computation that only overflows at 32 bits) would stay green in CI and ship to exactly the boards at risk. This is the mirror of S5-08: not a build tag, an architecture gate that CI never satisfies.
- **Fix (LESS NOT MORE):** One added step in `edge.yml`'s existing test job: `GOARCH=386 go test ./internal/smb/ -run TestReadCountCannotWrapNegative -count=1` (pure-Go package path; no cgo needed). Seconds of CI time, no new tests.
- **Benefit:** The blocker-class defect this test was written for (silent short reads on the target hardware class) becomes guarded where it can actually recur.
- **Effort:** S · **Risk:** Low · **Confidence:** High (READ)

### S5-10 / The suite's only fuzz target is never fuzzed: CI runs its three seed inputs as an ordinary test and no workflow passes `-fuzz`
- **Category:** Environment-gated test, degraded in CI

### S5-11 / Duplicated test scaffolding across the udpfs package: six server-bootstrap helpers, two identical locked-buffer types, and two near-identical DREAD listing helpers — ~140 lines recoverable in one package
- **Category:** Duplication (LESS NOT MORE)
- **Locations:**
  - Bootstrap: `internal/udpfs/integration_test.go:28-61` (`startTestServer`, 34 lines), `internal/udpfs/integration_test.go:229-258` (`startServerOnIP`, 30), `internal/udpfs/write_test.go:29-59` (`startServerAt`, 31), `internal/udpfs/blockdev_test.go:29-73` (`startBlockServerFull`, 45), `internal/udpfs/udpwrite_test.go:208-237` (`startBatchServer`, 30), `internal/udpfs/observability_test.go:48-94` (`startObservedTestServer`, 47) — 217 lines total, each repeating the same core: build `Config` → `New` → `Listen` → `Addr` → `Serve` in a goroutine → `t.Cleanup` with cancel + 2 s stop-wait + error check.   - Buffers, **same package**: `internal/udpfs/observability_test.go:24-39` (`synchronizedLogBuffer`) and `internal/udpfs/session_summary_test.go:22-37` (`lockedBuffer`) are the same mutex-guarded `bytes.Buffer` with `Write`/`String`, under two names (~16 lines each).
  - Listing: `internal/udpfs/compression_operations_test.go:77-102` (`listUDPFSImages`) and `:195-219` (`listUDPFSImageNames`) share the whole DOPEN → DREAD-loop → name-extraction → CLOSE body (~25 lines); they differ only in whether the size is also recorded.
  (Not counted, different packages and therefore not shareable without a new test-util package: the three `lockedBuffer`s in smb/udpbd/udpfs, the `discardWriter`s, and `writeContainer`/`writeUDPFSContainer`. - **Effort:** M · **Risk:** Low (test-only, mechanical; the risk is tedium, not behaviour) · **Confidence:** High (READ — line counts are from the files as pinned)

### S5-12 / `inRange` is genuinely boundary-tested — except the two cases its own arithmetic makes interesting: `count > sectorCount` from sector 0, and a non-sector-multiple image size
- **Category:** Boundary gap in an otherwise exemplary test (weak-but-real, filed for completeness because the task named this check)
- **Locations:** `internal/udpfs/blockdev_test.go:287-317` (`TestBlockRangeCheckSurvivesIntegerOverflow`); the function at `internal/udpfs/blockdev.go:87-92`. Fixture: `dev := &blockDevice{size: 64 * 512, sectorSize: 512}` (`blockdev_test.go:288`).
- **Problem:** What **is** covered, and should not be re-raised as missing: hostile near-`MaxInt64` sector (`MaxInt64-4, 8`), exactly `MaxInt64`, negative sector, zero count, negative count, one-past-the-end (`64, 1`), straddling the end (`60, 8`), and the valid edges `0,1` / `0,64` (exact full image) / `63,1` (last sector) / `32,32` (exact to the end) — plus the same overflow over the wire for both BREAD and BWRITE (`:322`). That is a real boundary test of the subtraction form `sector <= sectorCount()-count`. Two cases remain:
  1. **`count` greater than the whole image from sector 0** — `(0, 65)`, and the extreme `(0, math.MaxInt64)`. This is the case where `sectorCount()-count` goes negative; the straddle case `(60, 8)` reaches a negative RHS too, so the *mechanism* is arguably covered — but the direct form a client sends (sector 0, absurd count in the 16-bit count field's Go-level equivalent) is absent, and `(0, MaxInt64)` is the one input where a future refactor back to an additive form overflows on the *count* side rather than the sector side.
  2. **A size that is not a multiple of the sector size.** `sectorCount()` truncates (`blockdev.go:73`); every `inRange` test uses exactly `64*512`. The partial-tail behaviour is covered at *server* level (`blockonly_test.go:32`, a `64*512+17` image reporting 64-sector capacity) but never at the unit level for `inRange(64, 1)` / `inRange(63, 1)` against a `+17` size.
- **Fix (LESS NOT MORE):** Add three rows to the existing `hostile`/`valid` tables — `{0, 65}`, `{0, math.MaxInt64}` hostile; and a second `dev` with `size: 64*512+17` asserting `(63,1)` valid and `(64,1)` hostile. ~6 lines inside an existing test, no new test function.
- **Benefit:** The most-praised function in the Go tree (round 3) gets the last two corners of its truth table pinned.
- **Effort:** S · **Risk:** Low · **Confidence:** High (READ)
