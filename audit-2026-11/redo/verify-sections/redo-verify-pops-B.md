### RE-POPS-005 — VERIFIED
READ CAPACITY(10) semantics confirmed and no correction exists anywhere. `usbmass_bd/src/scsi.c:173-176`: `bd->sectorSize = getBI32(&rcd.block_length); bd->sectorCount = getBI32(&rcd.last_lba);` followed immediately by two divisions by `bd->sectorSize` in the `M_PRINTF` at :176. My grep for every `sectorCount =` assignment in the whole tree returns only this site, `bd_cache.c:186` (a verbatim copy `cbd->sectorCount = bd->sectorCount`), and the MBR/GPT partition assignments — **no `+1` anywhere**, so `last_lba` (address of the last block, per the `read_capacity_data` struct at scsi.c:41-45) is stored as a count: device is one sector short, a 1-sector device reports 0. `bd->sectorCount` is `u64` (`bdm/include/bdm.h:36`, "Maximum number of sectors usable") but is fed the raw 32-bit value. `block_length == 0` → integer divide-by-zero at :176 (both `(1000*1000)/bd->sectorSize` and `(1024*1024)/bd->sectorSize`). FatFs limb also exact: `ffconf.h:196-197` sets `FF_MIN_SS == FF_MAX_SS == 512`, and the sector-size sanity check sits at `ff.c:3387` (inside the `#if FF_MAX_SS != FF_MIN_SS` block at :3385-3388) — the report's line cite is precisely right, and the check is compiled out. Fix (`last_lba + 1`, reject non-power-of-two/out-of-[512,4096] `block_length` in warmup) is sane and LESS-compliant; saturation is unnecessary for a 32-bit source widened to u64 but harmless.

### RE-POPS-007 — VERIFIED
`usb_mass.c:616-665` (`usb_mass_connect`): endpoint taken at :659 from `sceUsbdScanStaticDescriptor(devId, NULL, USB_DT_ENDPOINT)` and passed unchecked at :660 to `usb_bulk_probeEndpoint`, whose first act is `endpoint->bmAttributes` (:546) — a device with no endpoint descriptor in its static set is a NULL dereference. The walk at :662-665 steps `endpoint + endpoint->bLength` for `i = 1 .. epCount-1` (`epCount = interface->bNumEndpoints`, :658) with no `bLength` floor and no bound: `bLength == 0` re-probes the same descriptor, any other bad value walks out of the config block. `usb_mass_probe` (:600) checks only `wTotalLength < sizeof(config)+sizeof(interface)` as a minimum-size test; `connect` never uses `wTotalLength` as a bound and re-derives `interface = config + config->bLength` (:652) without re-checking probe's class/subclass/protocol/`bNumEndpoints >= 2` conditions (:609). If anything the report understates it: `connect` also dereferences `device`/`config`/`interface` themselves with no NULL check (:648-656) — see Candidates. Fix (NULL-check + `bLength >= sizeof(UsbEndpointDescriptor)` + stay within `config + wTotalLength`) is sane.

### RE-POPS-008 — WEAKENED
The cited code is exactly as described — `usbd/src/hcd.c:192-193`: `if (data) descBuf = data + ((UsbDeviceDescriptor *)data)->bLength;` with no validation of that first step, and the loop at :200-204 then bounds- and `bLength >= 2`-checks. **True scope is narrower than the report's framing.** The loop condition is `((u8 *)descBuf < (u8 *)dev->staticDeviceDescEndPtr) && (descBuf->bLength >= 2)`; C short-circuit evaluation means a first step that lands at or past `staticDeviceDescEndPtr` is **not** dereferenced — the function just returns NULL. So there is no unbounded out-of-bounds dereference here. What actually remains: (1) a first step landing *inside* the block but off a descriptor boundary (device-supplied device-descriptor `bLength`, e.g. a small/forged value) makes the scan interpret interior bytes as descriptors and can return a bogus descriptor pointer that callers (hub.c:682/686, usb_mass probe/connect) then dereference as a real interface/endpoint; (2) a pointer landing exactly at `EndPtr - 1` passes the `<` test and the `bDescriptorType` read touches one byte past the block. Both are real but materially less than "a pointer that may already be out of bounds" being dereferenced. The proposed one-guard fix is still correct and cheap. Verdict WEAKENED on consequence, not on the code fact.

### RE-POPS-016 — VERIFIED
`scsi_cmd_rw_sector` (scsi.c:101-118) builds READ(10)/WRITE(10) (`0x28`/`0x2a`) and emits only LBA bits 0-31 (:112-115 mask/shift the low 32 bits of the u64 `lba` parameter; bits ≥32 are silently dropped = aliasing onto the start of the disk), and warmup uses READ CAPACITY(10) (:94-99, :168-175). The file's own comment at :108-110 concedes the 2 TB limit. Nothing enforces the cap: per SCSI, READ CAPACITY(10) returns `0xFFFFFFFF` when the true last LBA exceeds 32 bits, and that value is stored verbatim as the device size (compounding RE-POPS-005), so a >2 TiB drive is mis-sized rather than rejected. The surrounding stack is genuinely 64-bit: `block_device` uses u64 sector fields (bdm.h:34-36), GPT parsing is u64, FatFs is `FF_LBA64 1` (ffconf.h:206) with exFAT. Qualification (not a correction to the mechanism): the cap is 2³² *sectors* — 2 TiB at 512-byte sectors, 16 TiB at 4 KiB sectors; the report's "2 TiB" follows the code comment and the 512-byte world the rest of the stack assumes. Not a duplicate of RE-POPS-005: 005 is the off-by-one + unvalidated `block_length` in the same three lines, 016 is command-width/saturation/aliasing; distinct mechanisms, correctly cross-referenced in the report. Minimal fix variant (detect `0xFFFFFFFF`, refuse) is LESS-sane; the (16)-command variant is justified as the report argues.

### RE-POPS-066 — VERIFIED-DRIFT
Core claim re-derived by full-tree grep: **no active `#define MINI_DRIVER` and no `-DMINI_DRIVER` in any Makefile exists anywhere in the tarball or the clone.** The only define-shaped hits are commented out — `//#define MINI_DRIVER` in `libbdm/src/include/module_debug.h:4` and `// #define MINI_DRIVER` in `bdm/src/include/module_debug.h:4` (and its `__bdm_assault` copy) — in different components whose headers the USBD build does not include. So the `#ifndef MINI_DRIVER` branches in `usbd/src/usbd.c:33`, `driver.c:273`, `hcd.c:522` are unreachable as a configuration, and the shipped USBD always takes the large table. Corrected figures, from `usbd.c:33-61` read directly:

The report's Benefit claim that "requests … scale directly from these fields" is therefore wrong for IoReqs (per-device static-descriptor *total* does halve, via maxDevices, since `initHcdStructs` sizes it `maxDevices * maxStaticDescSize`, hcd.c:378).
- The thread stacks are not "halved": both sites go 0x4000 (16 KiB) → 0x0800 (2 KiB), an 8× cut.
- The report's clause "in the merged tree the symbol survives only as the unrelated printf-suppression switch in module_debug.h" is inaccurate as written: the merged `__usbd_bd_assault` tree retains the full `#ifndef MINI_DRIVER` config and stack branches (`usbd_usbd.c:33`, `usbd_driver.c:273`, `usbd_hcd.c:522`); the printf-suppression uses are in the usbmass_bd/bdm/libbdm `module_debug.h` files.
None of this rescues the MINI configuration — it is dead — but the savings estimate must be restated without IoReqs and with the correct stack ratio. Fix options (define it after a hardware smoke test, or delete the table) are both LESS-sane.
