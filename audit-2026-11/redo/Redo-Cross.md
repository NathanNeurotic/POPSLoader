## Method and rules applied

- THE MAIN RULE: LESS, NOT MORE — fixes favour removing divergence, deleting stale copies, or porting the sibling fix that already exists; no new abstractions.
- Wire layouts compared field-by-field across every implementation (C clients, Go, Python). Censuses and identity claims by script (sha256/diff/cmp), never estimated. One mechanism = one finding with every location.
- Dedupe: where a per-repo redo section appears to file a single-repo defect, the RE-X finding covers only the cross-repo aspect (divergence state, fix propagation), which is itself the finding. Negative results are recorded at the end, not manufactured into findings.
- Headline mechanisms (RE-X-01, RE-X-13, RE-X-15, RE-X-20, RE-X-22) were re-read first-hand by the coordinator in the clones during consolidation.

## Findings

### RE-X-01 — RiptOPL UDPRDMA receive copies a wire-controlled app-header length into fixed buffers; SMS already clamps it
- Category: 6 (bugs/security)
- Locations: RiptOPL `modules/network/udpfs_shared/src/udprdma.c:185-199` (used by all three variants) / Simple-Media-System `iop/SMSUdpfs/udpfs/src/udprdma.c:186-214` / both repos' `udprdma_packet.h` (`hdr_word_count:4` ⇒ `hdr_size` up to 60)
- Problem: `hdr_size = hdr_word_count * 4` comes straight off the wire (up to 60 B). RiptOPL feeds it unchecked to `smap_fifo_read(0x30, s->rx_hdr_buffer, hdr_size)` where the caller's buffer is exactly `rx_hdr_size` bytes (8 B for `udpfs_msg_result_reply_t`), and to a `dummy[UDPRDMA_MAX_APP_HDR]` (32 B) stack array in the skip branch. A version-skewed, buggy, or hostile server overflows the IOP stack from the SMAP RX thread; `rx_hdr_size` exists in the socket struct and is never read on this path. SMS's fork already fixes exactly this: copy only when `hdr_size <= s->rx_hdr_size`, otherwise drain the FIFO in 32 B steps (draining is mandatory — leaving the bytes desyncs every following payload read). Coordinator-verified first-hand in both files.
- Fix: Port SMS's clamp-and-drain branch into the shared RiptOPL `udprdma.c`, identical in behaviour.
- Benefit: Removes a remotely triggerable IOP stack overflow; restores client parity. Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-02 — RiptOPL read path returns a wire-controlled byte count from an uninitialised reply struct; SMS zero-inits and clamps
- Category: 6 (bugs/security)
- Locations: RiptOPL `modules/network/udpfs_shared/src/udpfs_core.c:89-117` (`_recv_with_result`) / Simple-Media-System `iop/SMSUdpfs/udpfs/src/udpfs_core.c:91-135`
- Problem: (1) `udpfs_msg_result_reply_t result` is declared uninitialised; if the server's app header is undersized/oversized, parts of it are never written (see RE-X-01's drain case) yet `result.msg_type`/`result.result` are read and trusted. (2) On success the function returns `result.result` unchecked: a server reporting more bytes than it DMA'd makes the caller hand the EE a count larger than the requested buffer, surfacing unwritten buffer bytes as file data. SMS fixes both: `= {0}` initialisation and `if (result.result > ret) return ret;`.
- Fix: Zero-initialise the reply struct and clamp the returned logical count to the bytes actually received, as SMS does; apply the same zero-init to the other stack reply structs in the same file read after a possibly-short header.
- Benefit: A misbehaving server degrades to a clean `-EIO` instead of bogus byte counts / leaked buffer contents. Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-03 — A pre-hardening copy of the UDPFS Python server ships inside RiptOPL with none of the current server's wire-value validation
- Category: 6 (bugs/security) / 2 (duplication)
- Locations: RiptOPL `ship/Example/APP_RIPTOPL-OFFICIALROLLING-VERSION.ZIP/neutrino/udpfs_server/udpfs_server.py` — `MAX_HANDLES = 32` (:101), `MAX_WINDOW_RETRIES = 4` (:106), `_handle_read` with no size cap (:908-937), `_handle_write_data` with no assembled-size cap and no no-write-in-progress guard (:974-1001), `_handle_bread`/`_handle_bwrite_req` with no total-size or offset-overflow refusal (:1267-1343) / PS2-Servers `udpfs_server/udpfs_server.py` — `MAX_HANDLES = 64` (:228), `MAX_WINDOW_RETRIES = 200` (:275), caps at :1983, :2051, :2114, :2508, :2585, write-state reset at :2010-2029
- Problem: The shipped copy is the same protocol with the safety removed: a single unauthenticated READ datagram can request a 4 GiB allocation (`size` is a raw u32), WRITE_DATA chunks can grow the assembly buffer without limit, BREAD can request ~32 MiB in one allocation, oversized sector offsets go unanswered instead of refused, and chunks from a refused write can land in the previous write's buffer. Anyone who runs the server from the shipped Neutrino example — the copy a user is most likely to actually launch — gets the vulnerable version, while the fixed version lives in another repo.
- Fix: Replace the shipped copy with the current PS2-Servers Python server (or, if the example must stay frozen, delete the server from the example and point at the PS2-Servers copy). Do not hand-port the individual caps — that recreates the drift that caused this.
- Benefit: The copy users actually run gains the transfer caps, writable-handle checks, and write-state reset the current server already has. Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-04 — Standalone UDPBD Python server range-checks READ only for raw devices and WRITE not at all; the Go server refuses out-of-range for both
- Category: 6 (bugs/security)
- Locations: PS2-Servers `udpbd_server/udpbd_server.py:205-236` (`_handle_read`: capacity check at :208 only when `bd.is_raw`; file-image reads past the end are zero-padded by design at :123) and `:238-261` (`_handle_write`: no capacity check before seeking/arming `_write_left`) / PS2-Servers `native/ps2servers-edge/internal/udpbd/server.go:370-385` (READ refused if `sectorNr+sectorCount > sectorCount()`) and `:440-451` (WRITE refused on the same test)
- Problem: Against the Python server, a WRITE request naming sectors past the end of a file image is armed anyway; the following WRITE_RDMA data is written at that offset, extending/growing the image file beyond its declared capacity — the exact quantity the INFO_REPLY advertises. READ behaviour also differs by backing type within the Python server itself (raw ⇒ error, file ⇒ padded stream), while Go uniformly refuses. The C client self-limits to 32 sectors per request but places no bound on the sector number it can be driven to request.
- Fix: Apply Go's refuse-out-of-range test in the Python server's `_handle_read` (for file images as well as raw devices) and `_handle_write`, answering/logging the refusal the way its existing raw-device read path does, instead of arming the write.
- Benefit: A disk image's advertised capacity becomes a real bound on both servers; no silent image growth from a stray or hostile request. Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-05 — Python and Go UDPFS servers disagree on BWRITE completion: Python silently truncates over-delivered data and reports 0, Go requires exact length and reports the byte count
- Category: 6 (bugs/security)
- Locations: PS2-Servers `udpfs_server/udpfs_server.py:2156-2187` (`_complete_bwrite`: writes `data[:expected_size]`, reports `_send_write_done(addr, 0)`) and `:2083-2132` (`_handle_write_data`: only the global transfer cap bounds assembly) / PS2-Servers `native/ps2servers-edge/internal/udpfs/blockdev.go:329-357` (`completeBlockWrite`: `len(buf) != expected` ⇒ `-EINVAL`, success reports `len(buf)`) and `internal/udpfs/operations.go:630-641` (per-chunk stop the moment a BWRITE exceeds its declared length)
- Problem: For the same wire sequence the two servers do different things with a length mismatch. Python accepts a BWRITE whose delivered bytes exceed the declared sector count, silently discards the excess, accepts a short delivery as a short write, and answers WRITE_DONE 0 either way — the client cannot tell a full write from a truncated one. Go refuses the write outright on any mismatch and additionally stops assembly per-chunk at the declared length, so a client declaring one sector cannot make the server buffer up to the full 8 MiB cap. The C client's write helper returns `done->result` to its caller (`udpfs_core.c:230-236` in both C clients), so the success value itself also differs by server (0 vs byte count) for identical requests.
- Fix: Make Python match Go: track the BWRITE declared length during chunk assembly, refuse (WRITE_DONE `-EINVAL`, buffer discarded) as soon as delivery exceeds it and on any final length mismatch, and report the byte count on success.
- Benefit: One BWRITE semantics across servers; silent truncation of block writes (VMC/HDD image writes) becomes a visible error. Effort: M · Risk: Low · Confidence: High (READ)

### RE-X-06 — SMS block read treats EOF/short reads as full success and leaves stale bytes in the caller's buffer; RiptOPL already handles both
- Category: 6 (bugs/security)
- Locations: Simple-Media-System `iop/SMSUdpfs/udpfs/src/udpfs_core.c:699-724` (`udpfs_core_bread`) / RiptOPL `modules/network/udpfs_shared/src/udpfs_core.c:664-695`
- Problem: SMS's loop only fails on `ret < 0`. On `ret == 0` (EOF) it still advances `sectors_left`/`sector`/`buffer` by the full chunk and ultimately returns the full requested `count`; on a short read (`0 < ret < chunk * sector_size`) the unwritten tail keeps whatever the caller's buffer previously held and is reported as disc/file data. RiptOPL treats `ret <= 0` as `-EIO` and `memset`-zeroes the short-read tail before advancing.
- Fix: Port RiptOPL's two behaviours into SMS's `udpfs_core_bread`: fail on zero-length result, zero-fill any short-read tail.
- Benefit: No stale-memory-as-sector-data and no false full-count success at end-of-file/image. Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-07 — SMS's SMAP FIFO read still drops the last byte of odd-sized frames; RiptOPL and Launchstation both carry the fix
- Category: 6 (bugs/security)
- Locations: Simple-Media-System `iop/SMSUdpfs/smap/src/xfer.c:144-148` / RiptOPL `modules/network/udpfs_smap/src/xfer.c:144-156` / Launchstation `iop/udpfs_smap/src/xfer.c` (same fix; documented in Launchstation `iop/udpfs_smap/ORIGIN.md`)
- Problem: SMS's `smap_fifo_read` PIO tail stores u32 chunks then a single u16 for a trailing 2 bytes, and has no step for a trailing single byte (or the 3rd byte of a 3-byte tail). The FIFO pads frames to 4 bytes, so every odd-sized UDPFS transfer — e.g. the end of every odd-sized file — leaves its final byte as stale buffer content. This is transport-level, so it corrupts data below the protocol layer regardless of RE-X-01/02/06. RiptOPL (and Launchstation, independently) read the final padded word once and store only the valid bytes.
- Fix: Replace SMS's u16-tail block with the read-final-word/store-valid-bytes loop the other two repos use.
- Benefit: Byte-exact file reads over UDPFS in SMS; removes a silent one-byte corruption. Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-08 — SMS's send path accepts any ACK as covering the sent packet (stale-ACK check is arithmetically inert); RiptOPL waits on the same timer with a real coverage test
- Category: 6 (bugs/security)
- Locations: Simple-Media-System `iop/SMSUdpfs/udpfs/src/udprdma.c:612-618` (and the duplicated logic in `udprdma_send_ll`, :681-687) / RiptOPL `modules/network/udpfs_shared/src/udprdma.c:369-389` (`_wait_ack`) + `modules/network/udpfs_ioman/src/udprdma_seq.h:8-11` (`udprdma_ack_covers`, identical copy in the bd/fhi variants)
- Problem: SMS computes `diff = (int16_t)((tx_seq_nr_acked − sent_seq_nr) & 0xFFF)`; the masked value is 0…4095, which as `int16_t` is never negative, so `diff >= 0 || diff < −2048` is always true — **any** ACK, including one for an older packet, completes the send as if the current packet were acknowledged. Where the check was meant to fire, SMS also spends one of only 4 retries and retransmits, provoking duplicate windows at the server. RiptOPL instead keeps waiting on the same alarm until an ACK whose 12-bit forward distance from the sent sequence is < 2048 arrives, or the real timeout fires.
- Fix: Give SMS the same cumulative-ACK coverage test and wait-without-retry loop RiptOPL uses (forward-half-ring covers, exactly-2048 ambiguous and not covering), in both `udprdma_send` and `udprdma_send_ll`.
- Benefit: Sends complete only on a genuine acknowledgement; fewer spurious retransmits/disconnects on lossy links. Effort: M · Risk: Medium (timing-sensitive IOP code; needs on-hardware soak) · Confidence: High (READ — the always-true condition follows directly from the read code's arithmetic)

### RE-X-09 — SMS ignores `SetAlarm` failure and can wait forever for an ACK/timeout that will never be signalled; RiptOPL fails the wait as a timeout
- Category: 6 (bugs/security)
- Locations: Simple-Media-System `iop/SMSUdpfs/udpfs/src/udprdma.c:602-603` (also :672, :730 — raw `SetAlarm(&clock, _timeout_cb, socket)` with the return value discarded) / RiptOPL `modules/network/udpfs_shared/src/udprdma.c:105-119` (`_arm_timeout`)
- Problem: Every SMS wait ends only on a packet flag or `EF_TIMEOUT`, and `EF_TIMEOUT` is raised only by the alarm. If `SetAlarm` fails (kernel heap exhausted, stale alarm still registered), the wait blocks indefinitely and UDPFS hangs for the session. RiptOPL wraps every arming in `_arm_timeout`, which on failure raises `EF_TIMEOUT` immediately so the caller's bounded retry loop still terminates the operation.
- Fix: Route SMS's three arming sites through an equivalent checked helper that signals the timeout flag when `SetAlarm` returns non-zero.
- Benefit: Removes an unbounded hang; failure degrades to the existing retry/disconnect path. Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-10 — Go UDPFS server returns all-zero timestamps (and zero attr) in OPEN_REPLY / DREAD_REPLY / GETSTAT_REPLY; Python returns real times
- Category: 6 (bugs/security — interop/semantics, low severity)
- Locations: PS2-Servers `native/ps2servers-edge/internal/udpfs/operations.go:464-472` (`sendOpen`: 36 B buffer, ctime/mtime never written), `:748-765` (`sendDRead`: attr @12 and all three times never written), `:809-816` (`sendGetStat`: same) / PS2-Servers `udpfs_server/udpfs_server.py:3056-3062`, `:3127-3135`, `:3150-3157` (all replies carry real ctime/atime/mtime)
- Problem: Layout is identical, so nothing fails loudly — but a client browsing the same share sees real file dates from the Python server and 00-00-0000 / zero dates from Edge, and any client logic comparing mtimes (sync, save-backup, "newer file" prompts) silently misbehaves against Edge. The Go reply builders allocate the full 36/48 B and simply never fill the time fields.
- Fix: Populate ctime/mtime (and atime where the struct has it) from the same `os.FileInfo` the Go handlers already stat, in PS2's 8-byte time format, matching what the Python builders emit; fill `attr` the same way Python does.
- Benefit: Identical client-visible metadata from both servers; removes a silent interop difference. Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-11 — Discovery header's second field is documented as "reserved, must be 0" in C but is the data port in both servers; the C client ignores it and trusts the UDP source port instead
- Category: 7 (build/CI/clutter — documentation/spec divergence with interop consequences)
- Locations: RiptOPL `modules/network/udpfs_ioman/src/udprdma_packet.h` (`udprdma_hdr_disc_t`: `service_id` + `reserved /* must be 0 */`; identical in SMS and in the bd/fhi copies) and `modules/network/udpfs_shared/src/udprdma.c:165` (on INFORM, `s->port = ntohs(disc_pkt->udp.port_src)` — source port, field never read; client sends the field as 0 at :266, :280) / PS2-Servers `udpfs_server/udpfs_server.py:492-504` (`DiscHeader.service_id, port`) + `:2655-2656` (INFORM carries `port = self.dsock.getsockname()[1]`) / PS2-Servers `native/ps2servers-edge/internal/protocol/packet.go` (`DiscoveryHeader{ServiceID, Port}`) + `internal/udpfs/negotiation.go:195` (INFORM marshals the data port)
- Problem: Three artefacts describe the same 2 bytes three ways. It works today only because servers set the field to the same value as their source port and clients ignore the field. Any future implementation written from the C header alone (field = 0, "reserved") breaks the servers' single-port / data-port negotiation, and any written from the Go/Python side (field = port) contradicts the only C documentation.
- Fix: Rename the field to `port` in the C header with a comment stating it carries the server's data port in INFORM (0 = use the source port), matching the Python/Go definitions; no byte changes anywhere.
- Benefit: The spec-in-code stops lying; the next implementation written from any one source interoperates with the others. Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-12 — RiptOPL carries three byte-identical copies of every UDPFS wire header (plus the ACK helper); SMS proves one copy per module is enough
- Category: 2 (duplication)
- Locations: RiptOPL `modules/network/udpfs_bd/src/`, `modules/network/udpfs_fhi/src/`, `modules/network/udpfs_ioman/src/` — in each: `udpfs_packet.h` sha256 `e51bb79a944c`, `udprdma_packet.h` `91f5d702d1c2`, `udpfs_core.h` `f3db57ee74ce`, `udprdma.h` `59d9692887d1`, `udprdma_seq.h` `08bf73e0b819` / Simple-Media-System `iop/SMSUdpfs/udpfs/src/` (single copies of the same headers)
- Problem: The real code already lives once in `udpfs_shared/` (the per-variant `.c` files are 122–125 B `#include` shims), but the headers that *define the wire format* are triplicated. A future wire fix must be made three times, and the three copies can silently drift apart while still compiling, producing IRX variants that speak different protocols. SMS's merged module shows the same three personalities build from a single header set.
- Fix: Delete two of the three header copies and point all three variant builds at one location (the shared directory the `.c` shims already use); keep exactly one copy of each header and of `udprdma_seq.h`.
- Benefit: One place defines the wire format; variant drift becomes impossible by construction. Effort: M · Risk: Medium (build-system change across three IRX variants) · Confidence: High (READ)

### RE-X-13 — Launchstation's dashboard starter `title.cfg` is written with spaced `title = / boot =` lines that RiptOPL's parser silently drops — the app vanishes from RiptOPL's Apps list
- Category: 6 (bugs/security)
- Locations: Writer: Launchstation `src/dash_apps.c:175-187` (`editMetadata()` starter template: `"title = %s\r\n"`, `"boot = %s\r\n"`) · Writer locked in by test: Launchstation `tests/test_opl_title_cfg.py:101` (asserts the spaced strings; never feeds the file to RiptOPL's parser) · Reader: RiptOPL `src/sources/appscan.cpp` (opens each APPS subfolder's `title.cfg` via `configRead`) · RiptOPL `include/appsupport.h:15-19` (`APP_CONFIG_TITLE "title"`, `APP_CONFIG_BOOT "boot"`) · RiptOPL `src/core/config.cpp:167-191` (`splitAssignment` — no trim on either side of `=`) · RiptOPL `src/core/config.cpp:1115-1182` (format latch; classifier at :129) · RiptOPL `src/core/config.cpp:257-265` (`ConfigSet::find` — exact key match) · RiptOPL `src/sources/appsupport.cpp:729-773` (`appScanCallback`; requires title+boot at :735, drops the app at :770)
- Problem: The starter emits `title = X` / `boot = Y`. RiptOPL's format latch only treats a line as libconfig if it has whitespace before `=` **and** ends with `;`; the starter has the whitespace but no `;`, so the file latches to the legacy parser. The legacy `splitAssignment` copies the key as everything before `=` with no trailing-space trim and the value with no leading-space trim, producing key `"title "` and value `" X"`. `ConfigSet::find` matches keys exactly, so lookups for `"title"`/`"boot"` miss, `appScanCallback` logs "APPSUPPORT item has no boot/title." and the app is never listed. RiptOPL's own comment at `src/core/config.cpp:85-103` documents exactly this failure mode and states its own writer emits `"%s=%s\n"` (writer at `config.cpp:1595`). CRLF is not the problem: RiptOPL strips a trailing `\r` per line. Launchstation never notices because its own reader trims both sides of `=` (`src/dash_store.c:53-102`), and every other `title.cfg` writer in either repo agrees on the unspaced form: Launchstation's `make_title_cfg` (`src/filer_actions.c:1924`, `"title=%s\nboot=%s"`), Launchstation's packager (`scripts/package_apps.py:116`), POPSLoader's shipped `bin/POPSLDR/title.cfg`, and RiptOPL's shipped example and packager. Coordinator-verified: the spaced format strings read verbatim in `dash_apps.c`.
- Fix: Change the one wrong writer: make the `dash_apps.c` starter emit `title=%s\r\nboot=%s\r\n` (unspaced, matching every other writer of this format), and update the host test at `tests/test_opl_title_cfg.py:101` to assert the unspaced strings. (Hardening RiptOPL's legacy parser to trim would also work but touches the parser every config flows through; LESS-NOT-MORE favours fixing the single writer that is out of step.)
- Benefit: Apps whose metadata was created from Launchstation's dashboard appear in RiptOPL again; the two launchers stop disagreeing about a file both claim is "OPL format". Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-14 — Same shared `title.cfg`, same concept, different key: Launchstation writes launch arguments as `arg=`, RiptOPL reads `argv1=` — each silently ignores the other's
- Category: 6 (bugs/security)
- Locations: Launchstation starter comment: `src/dash_apps.c:187` (`"# arg = first argument (one per line)"`) · Launchstation parser/consumer: `src/dash_lib.c:325-328` (`metaKv` accepts `arg`/`args`, case-insensitive, including in its OPL-style pass), `src/dash_lib.c:431-438` (`dashLibLoadArgs`), called from `src/dash_main.c:629` · RiptOPL: `include/appsupport.h:17` (`APP_CONFIG_ARGV1 "argv1"` — the only argument key), read at `src/sources/appsupport.cpp:761-765`
- Problem: Launch arguments are the one `title.cfg` concept both launchers implement, under two different key names. A user who adds `arg=` lines in Launchstation (its own starter template tells them to) gets a launch with no arguments in RiptOPL, and an `argv1=` written for RiptOPL is invisible to Launchstation. There are zero occurrences of `argv1` in Launchstation's src/include, and RiptOPL has no `arg=` handling. Unlike RE-X-13 this is not a parse failure — both files parse cleanly — it is a silent semantic divergence in a shared format.
- Fix: Pick one key for the shared file and have both sides honour it: the smallest change is for Launchstation's `metaKv` OPL-style pass to also accept `argv1` (RiptOPL's existing key, and the name its shipped examples use), and for its starter comment to name `argv1` instead of `arg`. Accepting both spellings on read costs one comparison; writing only the shared one stops the divergence growing.
- Benefit: Launch arguments set in one launcher take effect in the other; one less silent no-op in a file users hand-edit expecting both apps to honour it. Effort: S · Risk: Low · Confidence: High (READ)

### RE-X-15 — POPSLoader `ata_bd_fast`: LBA48 chunk counted in a `u16` — requests over 65536 sectors never advance (livelock)
- Category: 6 (bugs/security — hang)
- Locations: POPSLoader `iop/ata_bd_fast/ps2atad.c:1050` — `len = (u16)((nsectors > 65536) ? 65536 : nsectors);` (65536 truncates to **0**), then `:1081` `sceAtaExecCmd(buf, len, 0, len, …)`, `:1103` `buf += len * 512`, `:1105` `nsectors -= len` — with `len == 0` the `while (nsectors > 0)` loop re-issues the same transfer forever (the ATA count register's "0 means 65536" makes the transfer itself succeed, so nothing breaks the loop) · FIXED in both siblings by keeping a separate `u32 chunk`: Launchstation `iop/ata_bd/src/ps2atad.c:1052-1053, 1107-1109`; RiptOPL `modules/hdd/atad/src/ps2atad.c` (same `chunk` form)
