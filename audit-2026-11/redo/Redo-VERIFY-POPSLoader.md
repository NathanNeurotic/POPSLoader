## Method

Eleven parallel verification workers, one per domain chunk, under refute-first instructions, followed by coordinator spot-checks of **every** WEAKENED mechanism (and the one refuted limb, RE-POPS-091(d)) directly in the clone/tarball before consolidation — all coordinator spot-checks agreed with the workers. For every finding the verifier: (1) opened every cited file at the cited lines at the pin; (2) re-derived the mechanism from the code, hunting first for the defeating guard, constraining caller, or type that would kill it; (3) re-derived every hash, census, byte total, and occurrence count with their own scripts — no figure in the subject report was trusted; (4) judged the proposed fix for sanity and LESS-NOT-MORE compliance; (5) read bodies of neighbouring findings for mechanism-level duplicates. Per-chunk working files: `verify-sections/redo-verify-pops-{A,B,C,D,E1,E2,F1,F2,G1,G2,H}.md`.

Verdicts: **VERIFIED** (mechanism, citations, and figures hold) · **VERIFIED-DRIFT** (mechanism holds; some cited lines/values wrong — corrected values given) · **WEAKENED** (real but materially narrower than filed — true scope stated) · **REFUTED** (defeating evidence) · **BLOCKED-ENV** (cannot be settled in this environment). New defects noticed during verification are listed as candidates in §5, not verdicts. No PS2 build was attempted and nothing here is hardware-verified, matching the subject report's own limits.

## 3. Full reasoning — VERIFIED-DRIFT findings (27)

### RE-POPS-001 — mechanism and figures stand; whole-device manifestation belongs to 004
The read contract was traced end-to-end: the only leaf block device in the tarball is USB SCSI (`scsi_cmd_rw_sector` issues `bd->sectorSize * sectorCount` bytes; `usb_queue_cmd` passes `data_len` into the BOT CBW unclamped; per-URB chunking never clamps the total), so a 1-sector read really transfers `sectorSize` bytes on the raw path. GPT allocates `512 * 2` (header at +0, entries at +512); MBR allocates `sizeof(master_boot_record)` = 512 exactly (re-derived from the packed struct). Overflow arithmetic: S=4096 → 3,584 B past each 512 half — the report's figure is correct. **The drift:** on the primary whole-device first-touch path the report describes, the parsers do *not* receive the raw device — `bdm.c:60` wraps every whole device in `bd_cache_create` and `bdm_try_mount:156` hands drivers the cached bd, whose `_read` memcpy caps the caller copy at `count * 512` bytes; the oversized transfer lands in the cache's own 4 KiB slot, which is RE-POPS-004's overflow and fires first. The direct scratch overrun as written occurs on the raw path: `part_connect_gpt` has **no** `sectorOffset` guard (contrast `part_driver_mbr.c:24-25`), so GPT is probed against every partition device with the uncached bd and its LBA-1 read overflows the 1,024-byte allocation before the signature check can reject. MBR's raw overflow needs a crafted offset-0 partition. The proposed fix (size scratch from `sectorSize`; reject non-power-of-two outside [512, 4096]) is sane.

### RE-POPS-002 — iteration count corrected upward; BT sub-case pre-filtered
All four copies contain the identical walk with no NULL checks in connect, no `bLength == 0` guard, and no `wTotalLength` bound; the DS4 hardcode (`epCount = 20`, 21 iterations) is exact in the USB copies. **Corrected count:** `epCount` is a signed `int` in all four copies (`int pad, epCount;` / `int epCount;`), and `bNumEndpoints` is a `u8`, so `0 − 1` promotes to `int −1`. `do {…} while (epCount--)` then checks −1, −2, …, INT_MIN, then — in wraparound machine arithmetic — INT_MAX down to 1, stopping at 0: **2³² = 4,294,967,296 body executions**, not ~2³¹. Formally, decrementing past INT_MIN is signed-overflow UB, so the precise statement is "unbounded/UB; 2³² iterations under two's-complement wrap; the OOB walk crashes the IOP long before either count completes." The report understates by 2×. **Scope correction:** BT `bt_probe` rejects `bNumEndpoints < 3` (and checks `config == NULL`, `bNumInterfaces`, minimum `wTotalLength`), so the BT copies' zero-endpoint sub-case is defeated under the normal USBD probe→connect contract; BT remains exposed via `bLength == 0`, lying descriptors with `bNumEndpoints >= 3`, and unchecked NULLs inside `bt_connect` itself. Minor: a `bLength == 0` stall does not literally "re-open" the same endpoint — the per-direction guards suppress a second `UsbOpenEndpoint*`. The fix (NULL checks, real count, stop on `bLength == 0` or at `wTotalLength`, drop the hardcode) is sane.

### RE-POPS-003 — all four mechanisms present; the size arithmetic is worse than filed
(1) The hook scan (`pademu_hookSio2man:228`) uses `register u32 ctrl` against `u32 td->in_size`; `in_size < 3` wraps the bound to ~2³² and the scan reads/writes far past `td->in`, with the equality-only not-found test never firing on the wrapped path. **Correction:** the second scan, in `pademu():314`, uses `cmd_size`, declared `u8` — the wrap still occurs in the promoted comparison, but the index cycles 255→0, so that copy reads at most `td->in[0..257]` while potentially never terminating, rather than walking unboundedly far. (2) `pademu_cmd` reads `in[3]`…`in[9]` per command with no length check anywhere. **Corrected arithmetic:** at `pademu.c:415`, `PAD_GET_DATA(&out[3], out_size - 3, port)` — `out_size` (u8) is integer-promoted to `int`, so `out_size − 3` is **−3, −2 or −1**, and `get_data`'s `int size` passes it to `mips_memcpy(void*, const void*, unsigned)`, converting it to **4,294,967,293..4,294,967,295 bytes** — a catastrophic copy, not the ~253 bytes the report claims (that figure would require the subtraction to happen in u8 arithmetic, which C promotion rules do not do here). (3) `mtap_slot = td->in[2]` is stored unchecked at **:528** (the report's prose says :527, the preceding memcpy line) and used as `port`, indexing `pad[4]`/`ds34pad[4]`. (4) `pademu_mtap` switches on `td->in[1]` after only the multitap-address check. Fix direction is right; one caution: a blanket `in_size < 10` floor applied to `pademu_mtap` should be checked against legitimate short multitap transfers (its own cases need only `in_size >= 3` / `out_size >= 7`).

### RE-POPS-021 — fix as worded would break the default font
Mechanism exact: `fonts[16]` (`FNT_MAX_COUNT`), only `fntRelease` guards; `fntSetPixelSize`/`fntSetCharSize` call `fntCacheFlush(&fonts[fontid])` (which frees through the slot) and `fntRenderString`/`fntCalcDimensions` dereference `&fonts[id]`, all on a raw `luaL_checkinteger` with no range validation anywhere in the call path. Negative ids are realistic: `fntLoadFile`/`fntLoadbuff` return `FNT_ERROR` = −1 on failure. **The drift is in the fix:** "add the same range check `fntRelease` already uses" — copied verbatim, that check is `id > FNT_DEFAULT && id < FNT_MAX_COUNT`, i.e. 1..15, which **excludes id 0**.
