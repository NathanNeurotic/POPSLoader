================================================================================
EXECUTIVE SUMMARY
================================================================================

ROOT CAUSE: RPC Context Boundary Violation

The parent-context HDD ELF loading path (elf.c lines 627-898) violates a
fundamental PS2 architectural constraint: RPC client connections created in
one EE context become INVALID in another EE context after ExecPS2.

MECHANISM:
  1. fileXioInit() called in parent creates RPC client in parent context
  2. ExecPS2() switches to POPSTARTER's context
  3. POPSTARTER has no RPC client - parent's was lost
  4. POPSTARTER cannot read files or output debug
  5. Silent black screen result

SOLUTION: Use POPSLoader's embedded loader path
  - Already implemented in codebase
  - Known to work correctly
  - Initializes RPC in embedded loader's context (after ExecPS2)

PROOF OF ROOT CAUSE
================================================================================

PROOF 1: Both paths in same codebase (embedded loader works, parent doesn't)
  → Not a build issue, environment issue, or configuration issue
  → The architectural difference is the cause

PROOF 2: wLaunchELF avoids the problem by cleaning up RPC before ExecPS2
  → Explicit awareness of the constraint
  → Shows the problem is well-known in PS2 development

PROOF 3: Silent failure pattern matches RPC loss perfectly
  → No debug output = fileXio not working (used for logging)
  → Black screen = POPSTARTER can't initialize (needs files)
  → Perfect match for RPC context loss

PROOF 4: Module loading succeeds (partial success)
  → Modules load correctly
  → ELF loads correctly
  → Failure is in POPSTARTER's context, not earlier

PROOF 5: Code structure shows architectural awareness
  → Both working paths explicitly manage RPC lifecycle
  → Broken path does cleanup AFTER ExecPS2 (too late)

================================================================================
ARCHITECTURAL CONSTRAINTS DISCOVERED
================================================================================

Constraint 1: RPC Client Connections Are Per-Context
  - ExecPS2 creates new EE context
  - RPC client state cannot cross context boundaries
  - Each context must initialize RPC services in that context

Constraint 2: fileXioInit() Must Be Called In Execution Context
  - Creates RPC client in current EE context
  - Cannot be set up in parent and used by child
  - Each context needs to call it before using fileXio

Constraint 3: Module Loading Is IOP-Level (Global)
  - SifExecModuleBuffer loads into IOP (all contexts can access)
  - But RPC connections are per-context
  - Modules exist globally, connections don't

Constraint 4: IOP Mount State vs. EE RPC Client
  - Partition is mounted globally on IOP
  - But EE needs RPC client to access it
  - Parent's mount visible on IOP, but child has no RPC to use it

CONCLUSION
================================================================================

The POPSLoader HDD ELF loading silent failure is NOT a bug in module loading,
partition discovery, or ELF parsing. It is an architectural violation: 
attempting to use RPC services across EE context boundaries created by ExecPS2.

The solution is simple and proven: use the embedded loader path, which already
exists in the codebase and correctly initializes RPC services in its own context.

This is a common pattern in PS2 development (as proven by wLaunchELF). The
broken parent-context path appears to be an incomplete refactoring attempt.

Immediate action: Remove or disable the broken path (lines 627-898 in elf.c)
and verify all HDD execution uses the embedded loader path.
