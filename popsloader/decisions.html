2026-07-09 — Adaptive BDMA semantics: saved-mode-as-USB-preference, launch-cancel on staging failure, adaptive-off restage (800ac9c, 3eff270)

  • Decision: Adaptive BDMA (issue #509, PLDR.BDMA_ADAPTIVE, default Off — SUPERSEDED 2026-07-28: the default is now On, see the 2026-07-28 entry below) stages the launched device's BDMA variant at launch with an equipped-check-before-write. Three deliberate semantics: (1) the USB page resolves from the saved BDMA Mode — saved USBEXFAT keeps the exFAT pair, any other saved mode means FAT32 (modules removed); (2) a staging failure cancels the launch with a warn toast; (3) turning adaptive off restages the user's chosen mode in the same save (equipped-gated).
  • Rationale: (1) FAT32-vs-exFAT USB is not detectable from the launcher (identical BDM driver name, no fs-type binding), and a user whose drive needs the exFAT modules necessarily has that mode saved — it never worked any other way; (2) nothing queued after exec can render, and launching on wrong/half-written modules black-screens inside POPStarter with zero diagnostics — cancelling returns to the menu loop where the toast is visible (adversarial-review finding); (3) with adaptive on, bdma_mode.txt tracks the LAST LAUNCH, so without a restage the off-transition's marker reconcile would silently clobber the saved preference with whatever launched last (review finding).
  • Implications: the marker-override in ReconcileBdmaModeWithEffectiveState is gated on BDMA_ADAPTIVE ~= true; the marker file format is unchanged (mSAS reads it); no success toast exists — the tester pass signal is both-device launches booting; staging runs AFTER the cheap launch validations so a blocked launch costs no card writes; the POPSTARTER-folder interlock extends to the adaptive flag both ways.
  • Evidence: bin/POPSLDR/system.lua (MaybeApplyAdaptiveBdma/ResolveAdaptiveBdmaTarget/IsBdmaModeEquipped, the CommitSettingsChanges ON→OFF arm), bin/POPSLDR/ui.lua (Storage row + interlocks), review workflow wf_563626bc-4fe (8 confirmed findings, all actioned in 3eff270).

2026-07-09 — Partition-installed games are gated on an IMAGE0.VCD mount-probe, not partition name alone (198bae5)

  • Decision: the HDD (PFS) page lists HDDOSD/PSBBN partition-installed games (PP.<name> / __.<name>, image at pfs:/IMAGE0.VCD) discovered via the new HDD.ListPartitions() APA enumerator — but a candidate is listed ONLY if a read-only mount-probe finds IMAGE0.VCD at its root.
  • Rationale: name alone is a proven false-positive trap — HDDOSD apps also ship as PP.* partitions (e.g. CodeBreaker); the wLaunchELF source carries the same warning. The probe cost (one tracked RDONLY mount per candidate, once per boot under the HAS_CHECKED gate) buys a list with no phantom entries.
  • Implications: entries reuse the standard "PART|rel" encoding so cache/hide/R1/R3/launch routing flow unchanged; display + art/txt base = partition name minus the 3-char prefix (matches POPStarter's own __common/POPS/<name> convention); launch argv0 = the literal partition label + .ELF (case-sensitive, unsanitized); HDD sorts key on the DISPLAYED name (CompareGameEntriesByDisplay) since raw-encoded order put every PP.* above every __.POPS*. HW-unproven: the PP.<name>.ELF argv0 contract against the shipped r13 beta, and the wiki-documented old-launch-type __common asset bug (VMC scope).
  • Evidence: .research/wiki/hdd-mode.md + .research/firstparty/partition-games.md (R3Z3N); src/luaHDD.cpp ListPartitions; bin/POPSLDR/system.lua DiscoverPartitionGames.

2026-07-09 — Boot chime re-encoded at 22.05 kHz (e27103f; −190.9 KB, zero code changes)

  • Decision: bin/POPSLDR/boot.adp re-encoded 44.1 kHz → 22.05 kHz mono (390,912 → 195,472 bytes), full 15.51 s length kept.
  • Rationale: the audsrv APCM header carries the pitch; nothing in the C/Lua chain hardcodes the ADPCM rate, so the swap is code-free. Spectral analysis of the decoded original showed only 0.04 % of its energy above 11.025 kHz — the chime was a 44.1 k container around ~10 kHz content, so the halved rate discards nothing audible. Encoder = a faithful Python port of ps2sdk adpenc (roundtrip-verified: 34.6 dB codec SNR, flat per-band spectrum, exact frame math).
  • Implications: replacements need git add -f past the *.adp gitignore; keep the asset MONO (audsrv ADPCM is single-voice — a stereo file plays L-then-R sequentially); a hardware EAR check is still the only proof for SPU2 pitch handling — if it sounds wrong on a console, revert this one commit. A/B WAV previews live in the gitignored .research/_audio_preview/.
  • Evidence: Makefile embed rule (unchanged); src/sound.cpp / ps2sdk audsrv header semantics; the analysis pipeline in the session scratchpad (adp_pipeline.py).

2026-07-07 — SMB default Port = 1111 is DELIBERATE (rationale for 75e1a84)

Standard SMB servers listen on 445 — that is a documentation concern (README's SMB section + TESTING both tell users to set the Port to their server's real port), NOT a reason to change the default.   • Implications: RenderSmbConfig keeps the 445-implied convention (an explicit :1111 is written into SMBCONFIG.DAT); connect failures name the failing step so a port mismatch is self-diagnosable. Do NOT migrate persisted SMB_PORT values.
  • Evidence: maintainer statement 2026-07-06 ("Port 1111 should not be the issue, I use custom ports all the time thanks to my PS2-Servers repository"); bin/POPSLDR/system.lua SMB_FIELDS.

2026-06-30 — Selectable Cover/Details Folder (ART_LOCATION); the open()-vs-fopen() cover theory was DISPROVEN (7f9b5fa, 6641860, BETA-13-PLAY)

  • Decision: On REMOVABLE devices the cover .png + details .txt lookup folder is user-selectable via a new ART_LOCATION setting (Settings > Game List > "Cover/details folder"): pops_art (default) tries <device>:/POPS/ART/ first, pops uses the game's own POPS/ folder beside the .vcd, art tries a top-level <device>:/ART/. The game's own POPS/ folder is ALWAYS appended as a final fallback. HDD/PFS is unchanged (fixed hdd0:__common/POPS/ART/). CoverCache:GetOrLoad also drops its doesFileExist/open() existence pre-probe and lets Graphics.loadImage (fopen) open the file directly.
  • Rationale: a tester (FifthFox) reported covers not showing from a POPS/ART subfolder on USB/MX4SIO while a cover/.txt beside the .vcd worked. I first hypothesised an open()-vs-fopen() difference on nested paths. A source investigation (workflow w0ucpisvc, 4 agents, high confidence) DISPROVED that: in ps2sdk open() and fopen() both funnel through the SAME libcglue _open (ee/libcglue/src/glue.c -> __path_absolute in cwd.c; newlib fopen->_fopen_r->_open_r->_open, open->_open_r->_open), so they resolve mass:/POPS/ART/x.png byte-identically. Nested subfolder reads WORK on the BDM/FAT drivers: OPL reads mass0:/ART/<name>_COV.png + mass:/CFG/*.cfg with plain open() (.research/opl bdmsupport.c:585/588, textures.c:563, opl.c:2016, util.c:177), and ps2sdk FatFs follow_path() walks /-segments with no depth cap. POPSLoader's BuildCoverCandidates builds a correct mass:/POPS/ART/<name>.png for USB and MX4SIO. So the pre-probe drop is an INERT cleanup (one fewer redundant open() before the identical fopen()), NOT a fix; a POPS/ART cover that does not show is a filename/location/build-version issue, not a read-path limitation. The setting stands on its own as a usability feature (users pick where art lives). A directory-listing existence check was rejected (only proves existence; reads work anyway).
  • Implications: the pre-probe drop is behavior-neutral (loadImage still returns nil for a genuinely missing file, memoized in CoverCache.failed). Because open()==fopen(), a .txt in POPS/ART also reads fine when present (no separate limitation). To stop this costing test cycles, UpdateSelection stores the primary missed path (last_cover_probe) and the list view prints a "No cover. Looked for: " caption under the placeholder when preview is ON, text is shown, and no details occupy that space, so a tester self-checks the .png name/folder. ART_LOCATION sits between DETAILS_ALIGN and HDD_FS in EncodeSettings; persisted-key count is 22 + the appended SMB block.
  • Evidence: bin/POPSLDR/ui.lua BuildCoverCandidates (~190) + CoverCache:GetOrLoad (344, no pre-probe, corrected comment) + the missing-cover caption (list-view render); bin/POPSLDR/system.lua ART_LOCATION plumbing (encode 3339, default 3584, load 3703/3770). 2026-06-29 — Deterministic Removable-Device POPSTARTER Resolution: custom → cwd → device (BETA-13-PLAY)

  • Decision: For REMOVABLE devices (USB / exFAT-ATA / MX4SIO / MMCE), PLDR.ResolveLaunchPopstarterPath resolves POPSTARTER.ELF in one deterministic order: (1) an explicit user-configured absolute path (the custom-path setting, or any absolute Profile selection) when it actually resolves; (2) the game's own <device>:/POPS/POPSTARTER.ELF when it exists (lets a per-device build be used without enforcing it); (3) the launcher's own folder ("cwd") via the new ResolveCwdSidecarPopstarter (probes APP_DIR_LOCAL / live CWD / BOOT_ARGV0 / BOOT_PATH / APP_DIR_RAW, skipping HDD/pfs candidates); (4) the existing mc0:/mc1:/POPSTARTER + configured-default fallback net. (Initial cut was custom→cwd→device; flipped same-day to device-before-cwd so per-device POPSTARTER builds actually win — see the FifthFox USB-delay report.) This SUPERSEDES the ee4cba0 "prefer device-local first" precedence — device-local drops from first to step 3, so a configured custom path now wins as intended. Profiles need no UI change: an absolute Profile selection IS the step-1 custom path, so they act as presets that fill the custom field.
  • Rationale: eliminate new-user confusion / "cover them out of the box" — a launcher + POPSTARTER dropped together (cwd) just works, the per-device POPS/ folder is the catch-all, and an explicit custom path is always honored. Custom is existence-gated so a stale/typo'd path falls through to cwd/device instead of stranding a launch.
  • Implications: HDD/APA (internal PFS) resolution is INTENTIONALLY UNCHANGED — HDD games hit the colocated == nil early return and fall straight into the unchanged ResolvePopstarterPath, preserving the D-10/D-15 partition-context + embedded-loader path byte-for-byte (adversarially verified: HDD-equivalence + order-correctness PASS). The prior 2070a65 games-only-exFAT fix survives (the cwd/net still finds the MC-resident POPSTARTER). NEW behavior for removable devices → needs HW validation across USB/exFAT-ATA/MX4SIO/MMCE; device-local is ordered AHEAD of cwd so a per-device POPSTARTER build (e.g. a USB-delay build on the USB drive, a faster one elsewhere) wins for that device's games, while cwd + the mc-net still cover everyone else — intended (FifthFox USB-launch report). APA/internal-PFS now has its OWN ordered resolution (custom → hdd0:__common/POPS/POPSTARTER.ELF → cwd → net): the __common step resolves through the SAME path as the shipped bare-pfs __common profile (#2), so the D-10/D-15 partition-context + reboot_iop=1 + embedded-loader handoff is byte-identical to selecting that profile (3-skeptic verify PASS, no real bug); on a miss it releases the probe's slot-3 mount and falls to the unchanged boot-sidecar+mc resolver. Landed as a SEPARATE commit so it can be reverted alone — NEEDS a real-PS2 D-10/D-15 check before trust. The BDMA "modules located" picker idea was dropped: the driver variants are embedded in the ELF (no external source), and POPStarter reads them only from mc0:→mc1: ("Mass is not supported").
  • Evidence: bin/POPSLDR/system.lua ResolveLaunchPopstarterPath + new ResolveCwdSidecarPopstarter (~1786). 3-skeptic adversarial verify wf: HDD byte-identical + order-correct PASS; one unqualified-call bug caught pre-push (PopstarterProbeWithEnsure → PLDR.PopstarterProbeWithEnsure) and fixed. Landed on BETA-13-PLAY 2026-06-29; CI+Rolling green.

2026-05-28 — MX4SIO Evidence-Based Mass: Classification (PR #472 + refinement 7b587fe)
